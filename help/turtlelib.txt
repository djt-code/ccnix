turtlelib: shared helpers for the turtle programs

Usage in a program (same directory):
    local T = require("turtlelib")

Provides:
  * dead-reckoned position/heading (T.pos, T.dir, T.face), kept right by the turtle API itself: loading this wraps the moves and turns (forward, back, up, down, turnLeft, turnRight), the digs, places and attacks, once however many programs load it, so a move made straight through turtle.* is counted too; T.raw holds the originals
  * protected areas (T.protect, T.unprotect, T.protected, T.inside) that no dig through the turtle API goes into, and a refusal to dig chests, barrels, shulker boxes, spawners and ComputerCraft blocks (T.cfg.digContainers lifts it)
  * change hooks: T.onChange(fn) hears every successful dig, placement and move
  * T.moveTo: a move to a cell in three dimensions that says why it stopped (blocked, protected, lava), T.withPeripheral and T.equipPeripheral: use an item as a peripheral without taking off a chunk controller, T.pull: a count of one item out of a chest, and a junk chest (T.setJunkChest, T.isJunk, T.dumpJunk) that nothing is ever dropped on the ground for
  * the map and the frames (tl.world, loaded when first used): T.scan, the geo scanner's blocks in the turtle's own frame, kept in a map on disk (T.map.get/find/heights/slice, ...) that digs, placements and moves update, T.setOrigin/T.toWorld/T.toLocal for world coordinates, and T.inspectAt for block states; a re-zeroed frame (--here) keeps the map right
  * routes (tl.path, loaded when first used): T.path, A* over the map round lava, fire, doors and the player's furnishings (ladders, signs, torches, ...) and through protected areas only where the map knows they are empty (nothing in one is dug), and T.travel, which walks one along a clear layer (or the search), planning again at a block it did not expect; T.moveTo's opts.path asks for it
  * placing (tl.place, loaded when first used): T.placeAt puts a stair, slab, log, torch, door or the like down with the state wanted (facing, half, axis), choosing how to place it from a table of what each approach gives, checking and trying another way if the game differed, and remembering what it learnt; T.ignite lights a fire from above
  * building (tl.blueprint, loaded when first used): a plan is layers of text with a legend (T.blueprint.parse/fill/box/walls/fromMap); T.build puts one up layer by layer, materials checked first, progress kept so a stop or reboot carries on; T.verify says which cells differ, states included; T.replace swaps the blocks matching a glob in a box
  * the player's view (tl.lint, loaded when first used): T.lint warns of what stops a two-tall player in a build: headroom over stairs, a flight's approach and exit, railings meeting only on a diagonal, unrailed drops, a lantern at head height; T.walkable finds a way a player walks from one cell to another
  * light (tl.light, loaded when first used): T.light floods block light over the map; T.darkCells lists the cells where a mob could spawn
  * what a block holds (tl.attach, loaded when first used): T.attachedTo names the torches, ladders, signs and the like a dig there would drop; T.digCell's opts.attached refuses or warns
  * crafting (tl.craft, loaded when first used): T.craft makes stairs, slabs, walls, doors, chests and the rest of vanilla's building basics from a chest, through the crafting table equipped as a peripheral (a chunk controller stays on); recipes are data (T.addRecipe adds more), T.canCraft says what is short; T.smelt runs a furnace; T.fuelTicks and T.smeltsTo are what burns and what smelts
  * the chests at home (tl.store, loaded when first used): T.addChest tells it where they are, T.catalogue goes round them and writes down what each holds, T.where says which have an item, T.fetch goes and takes some, T.stow puts what it carries away (a chest for it, one holding it, the bulk chest), T.sortChests tidies, and T.cfg.autoDump = true does that on its own when the inventory nearly fills
  * taking blocks by name and fuel (tl.harvest, loaded when first used): T.harvest digs the blocks matching a glob in a place, nearest first and top down, leaving lava-touched, protected and falling-supported ones; T.refuelFromLava takes up the nearest lava source and burns it; T.fuelFor says what a route or build will cost
  * jobs, undo and reports (tl.journal, loaded when first used): T.job keeps a job's goal, steps and progress in a file so a restart carries on at the step; T.cfg.undo = true writes down each dig and placement and T.undo(n) puts them back; T.report tells the player (the setting turtle.player; everyone when it isn't set) through a chat box, with position, fuel and progress
  * modules loaded when first used: a function T lacks that is in T.registry is looked up there, its module (turtle/tl/<name>.lua, required as "tl.<name>") fills T in, and the call goes on
  * fuel management that refuels from inventory mid-task (T.ensureFuel)
  * low-level moves that only dig blocks listed in T.diggable
  * six directions (0..3 and "up"/"down"): look, dig, place or move in one, the fewest-turns ordering, 3D positions and keys
  * a learned 2D obstacle map with BFS routing (T.goTo)
  * two column-stepping strategies: flat (fixed height) and terrain (climb steps, follow the ground, refuse crevasses)
  * inventory helpers (items by name or by a test), tool hot-swapping, serpentine plan generation
  * chest-below helpers: dump with a keep policy, count, restock, merge part stacks
  * reading item names and saved files with lib/scan and lib/text, not Lua patterns; the files with lib/fileio
  * the programs' options (T.options, on lib/getopt) and mine's job file (T.loadMineJob, T.saveMineJob: mine and autostart read it)

Programs configure it by setting fields on T.cfg and T.diggable before moving.  Everything is relative to where the turtle starts: (0,0,0) facing +z, with +x to its right.

A turtle can't open doors or trapdoors, press buttons, set a repeater's delay or pass a nether portal (it gets "Movement obstructed"): the player tests those.  Put a block back with T.placeAt, which stands outside the cell, not by placing up from the hole.

== Position persistence ==

T.dataPath(name)
    The path of a data file kept next to the running program (/ccnix/turtle for one in the ROM), moving an old copy down the first time it's asked for.

    The programs moved from the repo's top folder into turtle/ on 2026-10-28; a file left up there (a job half done) is moved down the first time it's asked for, so `--resume` and `reset` still find it. A program in ccnix's ROM (/rom/ccnix/turtle) keeps its files in /ccnix/turtle, where its updates go too (the ROM is read-only); one from an install before ccnix (/cc-turtles/turtle) is moved there the same way.

    The program is the one that loaded this copy of turtlelib, whichever is running when the file is written: the wrapped turtle functions of a program that has ended keep its position beside it, not beside the next program.

T.savePos()
    Write T.pos, T.dir and T.mode to the position file, so a stop or a reboot can still find the way home. Raises "Terminated" if a Ctrl+T was held back (see T.run).

T.run(fn, ...)
    Run fn(...) so that Ctrl+T can't leave the saved position wrong: one that comes during a turtle command is held back until the move or turn is saved.

    Plain Ctrl+T stops a program wherever it's waiting, in the middle of a turtle command too: the turtle still moves or turns, but the program never records it, so its saved position or heading is off by one and going home from there goes astray. Under T.run a Ctrl+T that comes during a command (or a peripheral call) is held back until it's done: the program stops at the next saved move or turn (T.savePos), or the next ordinary wait (sleep, a key), whichever comes first.

T.loadPos()
    The saved position as { x, y, z, dir, mode }, or nil if there is none.

T.frameId()
    The number of the frame the turtle counts in: one more at each re-zero that moves 0,0,0 (0 before the first).

T.frameStale(stamp)
    Why a job saved in frame `stamp` can't be carried on now (a re-zero since), or nil if it can.

    The stamp is a frame's number (T.frameId), or "stale" for a job found in another frame before and marked so; no stamp (a job saved before frames were numbered) can be carried on.

T.clearPos()
    Delete the saved position file: the next job starts from home as (0,0,0).

T.startAtHome(force)
    Call at the start of a job: the turtle is at home, facing forward. If a saved position says otherwise, returns it instead of resetting so the program can warn the user.

    Where it does reset, the spot the turtle stands on becomes (0,0,0) in a new frame; the map (T.map, if one is kept) is told where that spot was in the old one, so it stays right. With no saved position (the file was deleted) and no T.clearPos before it, nobody knows where that was, and the map is marked unaligned (T.alignMap).

    With GPS (T.checkedPos), the saved position is checked first: corrected, found when it was lost, or (beyond T.GPS_REACH) returned as it is, the turtle being somewhere else.

== The position from GPS (ADR-0018) ==

T.checkedPos(again)
    The saved position, checked against GPS where there is GPS: the position, and a line saying what GPS changed.

    Third: true if GPS puts the turtle beyond T.GPS_REACH (nothing corrected: stop, and say the line). Fourth: true if there's no world origin and no saved position to set one from. Asked once a run; `again` asks again.

== The turtle API, wrapped once ==

T.claim()
    Make this module the one the wrapped turtle functions keep up to date. Loading turtlelib does it already; call it when another program's module may have loaded since (claude, after run_program).

T.owns()
    Is this copy of turtlelib the one the wrapped turtle functions keep up to date (the last loaded, or the last to T.claim)? A module's listener that acts for its program (the undo journal, autoDump) acts only while its copy owns the turtle.

T.onChange(fn)
    Call fn(event) for every successful dig, placement and move from now on, by any program on this turtle; event.kind is "dig", "change", "place" or "move", with x, y, z. Returns a function that removes the listener.

    For "dig", x, y, z is the cell, was the block's name and state the block's state table, as the inspect before it gave them; for "place", x, y, z is the cell, item the name of what was placed, if the slot's details have it, and block and state what the cell holds after (a torch item makes a wall_torch, seeds a crop; bone meal leaves the crop it grew); for "move", x, y, z is the cell it arrived at and from = { x, y, z }. A dig that left a block in the cell (a hoe tilling dirt into farmland) is kind "change", with was, and block and state for what is there now.

    A listener's error is dropped (except Ctrl+T), so one can't stop the turtle. Listeners last until the computer restarts: remove yours when the program ends.

T.protect(name, x1, y1, z1, x2, y2, z2)
    Protect the box between two corners (x, y, z in the turtle's frame, either order) under `name`: a dig into it returns false, "protected: <name>" (placing and moving in it are not stopped). True, or nil and why.

    It replaces a box of the same name.

T.unprotect(name)
    Remove the area called `name`. True, or false and why (none by that name).

T.areaSet(names)
    The names in `names` (one area's name, a list or a set of them) as a set { [name] = true }; an empty set for nil.

T.protected(x, y, z, skip)
    The name of the first protected area that holds the cell, or nil. `skip`, a name or a list of names, leaves those areas out (see T.guarded).

T.protections()
    The protected areas, as a list of tables with named fields: { name =, x1 =, y1 =, z1 =, x2 =, y2 =, z2 = } (p.name, p.x1, ...; copies: changing one changes nothing).

T.guarded(x, y, z)
    The name of the protected area that stops the current job from digging the cell: T.protected, but not counting the areas the job is working inside (T.cfg.inside, set by T.inside). nil if none.

T.boxOf(box)
    The six numbers of a box, the smallest corner first, or nil and why. A box is { x1, y1, z1, x2, y2, z2 } or has the fields x1 to z2, the corners in any order.

T.excludeTest(list)
    A test of cells against an opts.exclude list (protected areas' names and boxes): test(c) is true for a cell { x, y, z } in any of them. Nil and why for an entry that is neither.

T.inside(names, fn, ...)
    Run fn(...) as a job that owns the protected areas `names` (one name, or a list): digging in them is allowed meanwhile (other areas still hold). Puts it back after, even if fn errors (the error goes on); returns fn's results.

    A cell in two areas can be dug when the job owns both: T.inside({ "keep", "wall" }, fn). Inside another T.inside the job owns the areas of both.

T.withUnprotected(names, fn, ...)
    Run fn(...) with digging allowed in the protected areas `names` (one name, or a list): T.inside by another name.

T.neverDig(name)
    Is this block one the dig functions refuse (a container, spawner or ComputerCraft block)? mine's own list of blocks never to dig.

T.turnRight()
    Turn a quarter turn to the right, keeping T.dir and the saved position right.

T.turnLeft()
    Turn a quarter turn to the left, keeping T.dir and the saved position right.

T.face(d)
    Turn to face heading d (0 to 3, as T.dir) by the shorter way.

T.faceToward(x, z)
    Face toward an adjacent column.

T.posString()
    The position as "(x,y,z)".

T.setDir(d)
    The heading is really d (a program worked it out from what's round the turtle: the saved one can be off after a stop between a turn and its save, or a turtle put back by hand).

    Only the heading was wrong: the frame, and the map, protected areas and chests kept in it, stay as they are (the program worked d out from its own layout, which is in that frame).

T.lookAround()
    What's beside the turtle, by quarter turns to the right of the way it faces: seen[a] is the inspect data at a turns, or false for air.

    For checking the heading, so it turns with the raw turtle calls (which leave it facing as it was) and T.dir isn't touched.

== Fuel ==

T.hasFuel(n)
    Is there fuel for n moves? (Always, with fuel turned off.)

T.refuelTo(target)
    Burn fuel from the inventory until the tank holds `target`. Only what T.fuel lists is burnt: logs, planks, sticks, chests and crafting tables burn too, but they're what chests and torches are made from.

T.homeCost()
    Fuel to get home from here: straight-line moves by default. Programs that travel at a set height or dig down to a chest override it.

T.ensureFuel()
    Called before every move: when the tank is short of the trip home plus T.cfg.fuelMargin, tops it up from the inventory; if that isn't enough, runs T.fuelTrip, else waits for the user once truly out.

    On the trip itself, or with no T.fuelTrip set, it waits for the user once truly out, rather than starting another trip.

T.totalFuelAvailable()
    Fuel in tank plus the fuel value of the T.fuel items in the inventory. Burns nothing.

T.requireFuel(needed)
    Block until at least `needed` fuel is available (tank + inventory), filling the tank up to `needed` from inventory first.

== Tool upgrades ==

T.isTool(name)
    Is the item `name` a tool (a pickaxe, hoe, shovel, axe or sword)?

T.emptySlot()
    The first empty slot, or nil if there is none.

T.findSlot(what)
    The first slot holding `what` (an item name, or a function(name, item) that picks one); nil if none.

T.equipped(side)
    Name of the item equipped on `side`, or nil. Uses getEquippedLeft/Right (CC:Tweaked 1.110+); older versions are probed by swapping through an empty slot, which needs one free slot.

T.findTool(suffix)
    A tool whose name ends with `suffix` ("_pickaxe"): the one equipped, else the first in the inventory; nil if there's none.

T.usePrimaryTool(name)
    Equip `name` from the inventory if it isn't already, unequip any OTHER tool into the inventory, and return a function that restores the original arrangement. Errors if the tool is nowhere on the turtle.

    The tool hook (T.hooks.tool) is called first.

T.withTool(name, fn)
    Run fn with `name` as the only equipped tool, restoring the original tools afterwards even if fn errors (the error is re-thrown).

T.equipTool(name, side)
    Back-compat: equip `name` onto `side` from the inventory, if present.

== Peripheral upgrades ==

T.equipPeripheral(name, opts)
    Equip the item `name` on the side that holds no chunk controller (or kept side), and wait for it to show up. Returns the peripheral and a function that puts back what was there, or nil and why.

    It prefers an empty side, then one with a tool, then another upgrade; opts.free = true takes only an empty side or a tool's, so no upgrade comes off (a modem, a scanner). Call the returned function when done (calling it again does nothing). The reasons for nil: not on board, a tool rather than a peripheral, both sides kept, no free slot for what comes off, or it never showed up.

T.withPeripheral(name, fn)
    Run fn(peripheral) with the item `name` equipped as a peripheral, and put back what was on that side afterwards. Returns true and what fn returned, or nil and why it couldn't equip (see T.equipPeripheral).

    The side is put back even if fn errors (the error is re-thrown).

== Low-level moves ==

T.up()
    Move up one block, digging what T.diggable lists and attacking what's in the way (fuel first): true, or false and why. It stops at T.cfg.maxHeight, 16 above the start by default.

    Why is "maxHeight 16 reached (T.cfg.maxHeight)" (set it higher to climb), "blocked by <block> at x,y,z", "couldn't dig ...", "can't move up: ..." or "no fuel".

T.down()
    Move down one block, digging what T.diggable lists and attacking what's in the way (fuel first): true, or false and why. It stops at T.cfg.maxDrop, 12 below the start by default.

    Why is "maxDrop 12 reached (T.cfg.maxDrop)", "blocked by <block> at x,y,z" or the others T.up gives.

T.forward()
    Move forward one block, digging what T.diggable lists and attacking what's in the way (fuel first): true, or false and why ("blocked by <block> at x,y,z", "couldn't dig ...", "can't move forward: ..." or "no fuel").

T.back()
    Back up a block without turning (saves turning round to go back the way it came). It can't see or dig behind it: false and why if anything is there ("can't move back: something is in the way").

T.settle()
    Sink until resting on something solid.

T.toY(y)
    Climb or sink to height y in the current column.

T.toStartHeight()
    Return to y = 0.

T.below()
    What is directly below: a block name (or "air"), plus inspect details.

== Six directions ==

T.sideDir(side)
    The direction a side (CC's "front", "top", "bottom", as for chests) is in from the turtle as it faces now.

T.here()
    A copy of T.pos: { x, y, z }.

T.at(p)
    Is the turtle at p ({ x, y, z })?

T.posKey(p)
    The key "x,y,z" for a position p.

T.keyPos(k)
    Inverse of posKey: the x, y, z of "x,y,z" (whole numbers, as posKey writes them); nil if k isn't one.

T.dist(a, b)
    The taxicab distance between two positions.

T.neighbour(d)
    The block next to the turtle in direction d.

T.dirTo(p)
    The direction from the turtle to the block next to it at p.

T.look(d)
    Face direction d (0 to 3, "up" or "down") and inspect there: returns turtle.inspect's ok, data.

    What it sees is remembered a while (the last 256 cells), so T.liquidNear knows of lava the turtle looked at even with no map; and with the map module loaded and a map on disk, it goes in the map too (a look never starts one).

T.digDir(d)
    Face direction d (0 to 3, "up" or "down") and dig there, through the wrapped dig, so a protected area holds. Returns turtle.dig's results (false and why if it can't).

T.placeDir(d, text)
    Face direction d (0 to 3, "up" or "down") and place the selected item there; text is written on a sign. Returns turtle.place's results.

T.attackDir(d)
    Face direction d (0 to 3, "up" or "down") and attack there. Returns turtle.attack's results.

T.suckDir(d)
    Face direction d (0 to 3, "up" or "down") and pick up items there. Returns turtle.suck's results.

T.moveDir(d)
    Move one block in direction d (T.up/T.down/T.forward: digging what T.diggable allows, attacking what's in the way).

== Liquids and falling blocks ==

T.liquidNear(x, y, z)
    The liquid that would flow into the cell x, y, z (or a table { x, y, z }) if it were opened: its name and cell, or nil.

    Lava, or a water source (a waterlogged block too), beside the cell or above it, as far as the map and what the turtle looked at lately (T.look) know. Lava under it doesn't flow up, so it isn't counted; water whose state says it is flowing isn't either (the map's water from a scan has no state, so it counts as a source). T.moveTo and T.travel refuse to dig such a cell on their way unless opts.liquid, T.digCell too, and T.harvest leaves it.

T.isFalling(name)
    Does this block fall when what is under it goes (sand, gravel, concrete powder, an anvil, ...)?

T.cellSet(spec)
    The cells of a list or set (opts.digOnly) as a set of "x,y,z" keys, or nil and why.

    Each is "x,y,z" or { x, y, z } (fields or the three numbers in order); a set's keys are "x,y,z" too, and one cell { x =, y =, z = } on its own will do.

T.moveTo(x, y, z, opts)
    Move to x, y, z, digging only what opts.dig allows: true (and a warning, if any), or false, why, the block and cell that stopped it. opts: order, dig, digOnly, avoid, inside, liquid; path = true hands a blocked run to T.travel.

    It goes along the axes in the order opts.order names (default "yxz": up or down first, then x, then z). opts (all optional):
      dig     false (default), true, a glob, or a list or set of globs: the
              blocks it may dig on the way (a protected area, a chest or a
              computer is never dug)
      digOnly a list or set of cells ("x,y,z" or { x, y, z }, see T.cellSet):
              the only cells it may dig (whatever block is there, unless
              opts.dig says which); any other block stops it
      avoid   a glob, a list or a set: blocks it stops at rather than enter
              (default: lava, fire, doors and the player's furnishings:
              ladders, trapdoors, fence gates, signs, lanterns, torches,
              rails); {} avoids nothing
      inside  the name of a protected area the move may dig in, or a list of
              names (see T.inside)
      liquid  true: dig a cell even when lava or a water source is beside it
              or above it (T.liquidNear); by default that dig is refused
      path    true, or a function(x, y, z, opts): when a straight run is
              blocked, ask a route finder (T.travel, from the path module, if
              there is one; or this function) to take it the rest of the way
    The why is a sentence: "blocked by minecraft:obsidian at 3,12,-4", "protected: castle (...)", "avoiding minecraft:lava at ...", "digging minecraft:stone at 1,0,0 would release lava at 1,0,1 (opts.liquid = true digs it anyway)"; the cell is { x, y, z }. The warning, when a cell it dug has a falling block over it as far as it knows, is "dug 1,0,0 under minecraft:gravel, which may fall into it". The turtle stays wherever it got to. (T.cfg.maxHeight and maxDrop, a program's grid, don't apply.)

T.digCell(x, y, z, opts)
    Dig the one block at x, y, z and nothing else: go beside it (the path finder, digging nothing), dig it. True, the block's name (nil: it was empty) and a warning (sand over it); or false and why.

    It refuses what T.moveTo refuses: a protected cell (opts.inside names the area the job owns), a chest or a computer (T.cfg.digContainers), and a block with lava or a water source beside it or above it (T.liquidNear; opts.liquid digs it anyway), checked before it goes and again when it is there. It stands in a cell beside it the map (or what the turtle saw) shows empty, else one never seen, the nearest first, going there with opts.move (T.moveTo's opts, default { path = true, scan = false }; digging is turned off). The dig goes into the map as every dig does. The turtle stays beside the cell. opts.attached looks first at what the block holds, from the map (T.attachedTo: a torch on it, a ladder or a sign on its side, a lantern under it): "refuse" refuses a dig that would drop any (a maybe too), naming them; "warn" digs, and returns them as a fourth value, { attached = the list }, named in the warning (those surely held go from the map as air). A block the dig would destroy (glowstone gives dust; glass, its panes and ice give nothing) is refused, saying what it gives, unless opts.lossy = true.

T.trail()
    The breadcrumb trail: the cells the turtle moved through lately (up to 200), oldest first, as { x, y, z }; the last is where it moved to last.

    Every move through turtlelib or the turtle API adds to it, by any program; T.retrace walks it back. It lives in memory (a reboot starts it again) and moves with the frame when the turtle re-zeroes.

T.retrace(n, opts)
    Walk back along the trail over the last n cells (default all of it), skipping loops. True and the moves made, or false, why and the moves made.

    Each hop is a T.moveTo to the cell before, with opts (T.moveTo's: dig, avoid, path, ...; default none, so it goes only where it went before). A cell the trail passed through twice is a loop: from the later visit it goes straight on from the earlier one. The cells walked back are taken off the trail, so a second T.retrace goes further back, not forward.

T.turnsTo(d)
    Turns it takes to face direction d (none for up or down).

T.eachAround(skip, fn)
    Call fn(d) with each direction but `skip`, the fewest turns away first (so up and down, and the way it faces, come before any turn).

T.stepToward(p)
    A step toward p (nearer by taxicab distance), the one needing the fewest turns; nil when there.

== Obstacle map (2D, by column) and BFS routing ==

T.ckey(x, z)
    The key "x,z" for a column.

T.keyXZ(k)
    Inverse of ckey: the x, z a key ("x,z") was made from; nils if k isn't one.

T.markBlocked(x, z)
    Mark column x, z as blocked, for T.bfs and T.goTo.

T.clearBlocked()
    Forget every column marked blocked.

T.inBounds(x, z)
    Is column x, z inside the routing area (T.cfg.width and length, plus T.cfg.margin)?

T.bfs(tx, tz)
    Shortest column path from the current position to (tx,tz), or nil.

    Columns marked blocked are walls, and so are the ones outside the routing area. A program can also set T.edgeOK to a function(x, z, nx, nz) that says whether the step from column x, z into its neighbour nx, nz may be planned (mow, which knows the height of the ground, refuses a step up or down more than it can make).

== Column-stepping strategies ==

T.stepFlat()
    Flat: stay at the current height.

T.stepTerrain()
    Terrain: climb up to maxClimb to get in, then sink onto the ground. A drop deeper than maxClimb is a crevasse: back out and mark it.

T.goTo(tx, tz)
    Navigate to column (tx,tz) with BFS + re-planning.

T.coverColumn(x, z)
    Stretch the routing area (cfg.width/length) so it takes in column (x,z) too: a turtle stopped outside it, on a farm bigger than the defaults or one lying left of or behind home, would otherwise have no route at all.

T.goHome(opts)
    Return to the start from wherever the saved position says we are (used by the `reset` subcommands and home.lua). Returns true if home.

    Serpentine over the grid: columns along x, rows alternating in z. Tiles are counted OUT from the start: x = 1..w, z = 1..l (signed), so the start tile (0,0) is never part of the plan.

T.lightLattice(radius, width, length)
    Positions for light sources so that every tile of the grid is within taxicab distance `radius` of one. Returns a set keyed by T.ckey and an ordered list.

tl.attach: what hangs on a block or stands on it, and would drop if the block were dug

Loaded by turtlelib the first time T.attachedTo is used (T.digCell's opts.attached asks for it).  Cells are the turtle's own (the frame it counts in).

A torch on a block, a ladder on its side, a lantern hanging under it: in the game they break and drop when the block that holds them goes.  T.attachedTo reads the six cells round a block in the map and names what the block holds, by a table of names and a rule a name saying where its support is:
  top
      it stands on the block under it: a torch, redstone dust, a repeater, a rail, a carpet, a pressure plate, a standing sign or banner, snow, a candle, a cake, a plant
  below
      it hangs from the block over it: a hanging sign, a spore blossom, hanging roots, weeping or cave vines
  wall
      it hangs on the block behind it, its facing pointing away: a wall torch, a ladder, a wall sign or banner, a tripwire hook, a coral fan on a wall
  face
      a button or a lever, by its face: floor (top), ceiling (below) or wall (as wall)
  hanging
      a lantern: hanging from the block over it, else standing on the one under it
  lower
      a door or a tall plant: its lower half stands on the block under it (the upper half goes too)
  toward
      cocoa: its facing points at the log it grows on
  multiface
      vines, glow lichen, sculk veins: each face it has (north, up, ...) clings to the block that way
  vertical
      pointed dripstone: up stands on the block under it, down hangs from the one over it
  directional
      amethyst buds and clusters: on the block their facing points away from
  bell
      by its attachment: floor, ceiling; on a wall, which wall the rule leaves open (maybe)
  sides
      a wall hanging sign: on a block beside it, which one the rule leaves open (maybe)
The map has a block's state only when it was inspected (T.inspectAt, T.inspectAll; a scan gives names alone), and a compass facing needs the world origin (T.setOrigin): a block that could be held but whose state or origin is lacking is listed as maybe (sure = false).  What stands on what the block holds (a sugar cane's column, a door's upper half) goes with it and isn't listed.  Java 1.21.1's blocks; a mod's blocks the table doesn't know aren't listed.

    A torch, redstone, a rail, a carpet, a standing sign or a door on top; a wall torch, a ladder, a wall sign, a button or a lever on a side, facing away from it; a lantern, a hanging sign or a button under it (the overview has the table). tl.blueprint: plans of what to build: the format, building it, checking it, and swapping blocks in a place

Loaded by turtlelib the first time T.blueprint, T.build, T.verify or T.replace is used.  Cells are the turtle's own (the frame it counts in).

A plan is layers of text with a legend, bottom layer first.  As a file it reads:

  name: tower
  anchor: 10 64 -3
  B = minecraft:stone_bricks
  s = minecraft:stone_brick_stairs[facing=north,half=bottom]
  layer 1:
  BBBB
  B..B
  layer 2:
  ssss

Each character is a cell: "." is air, a space is "leave alone" (not built, not checked), anything else is looked up in the legend.  The text is a map seen from above with +z at the top, as T.map.slice shows one: the first line of a layer is the highest z, a column goes toward +x, the next layer is one up.  The anchor is the turtle-frame cell of the first character of the first line of the first layer.  A state is in brackets after the name, key=value separated by commas; a name without a namespace is minecraft:'s.  The same plan as a Lua table: { name, anchor = {x, y, z}, legend = { B = "minecraft:stone_bricks", s = "...[facing=north]" }, layers = { "BBBB\nB..B", { "ssss" } } } (a layer is a string of lines or a list of lines).  The helpers fill, box, walls and fromMap make one from code; put changes a cell.  A legend entry may give an order hint: "t = oak_slab[type=top] after 0,1,0" (as a table, { name = ..., after = { 0, 1, 0 } }) builds each of its cells after the cell that far from it (here the one above), whatever the order would have been.

T.build puts a plan up.  It checks the materials first (what is short, and what could be crafted if the craft module is there), then goes layer by layer from the bottom, standing over each cell and placing down; in a layer the plain blocks come first, then stairs and slabs, then what hangs on others (torches, ladders, buttons, trapdoors, gates), then doors, so a thing goes in after its support; a top slab with a stair on it goes in after the stair (then it is placed from below, against it), and the legend's hints are followed.  With order = "column" the blocks, stairs and slabs go up column by column instead, each column from the bottom, the columns in a serpentine (on to the nearest one left), so a wall costs a climb a column rather than a lap a layer; then what hangs and the doors, layer by layer.  A stair, slab, log, torch or door goes through T.placeAt for the state it names.  The plan is kept as text in the data file .build, and how far the build has got (the number of the last cell tried, the cells that failed, with why, and the order) in .build.progress, so a stop, a crash or a reboot carries on where it was, in the same order, with a plain T.build().  A build that spends over three times the fuel T.fuelFor gives for its cells stops and says it is circling.  A build never digs a block out of a cell it fills (T.replace swaps blocks).  A finished build can protect itself (opts.protect).

T.verify walks the plan and says which cells differ, states included: a cell with a state to match, or that the map has never seen, is looked at with T.inspectAll; the rest is read from the map.  T.replace swaps every block matching a glob in a box for another, each from its nearest free side; one with no free side is reported, never dug to.

== Building ==

T.build(plan, opts)
    Build a plan (opts.order = "column": walls for less fuel), materials checked first, progress kept, stopping if it circles. Returns true, info; false, why, info when it stopped or cells failed; nil, why when it couldn't begin.

    `plan` is a plan (table or text); nil carries on the build saved in the data file after a stop, a crash or a reboot. The same plan again carries on too (its failed cells tried again); a different plan while one has cells not yet tried is refused unless opts.restart (the refusal counts what was tried and what failed). One whose every cell was tried, some failing, doesn't stand in the way: the new plan starts, and info.previous = { name, failed } lists the old one's failures. It first counts what the cells still to do need against what is on board, and refuses if anything is short (the reply's third value lists { item, need, have, short }, and what T.canCraft says if there is such a function) unless opts.partial; cells with no item left fail one by one. A cell that fails is noted and the build goes on; the failed ones are tried again at the end of a later run (opts.retry = false leaves them). Nothing is dug out of a cell it fills: a block in the way is a failure. A cell the map already shows holding the block (with its state) is taken as done without a look, so a plan built over itself, or carried on after a crash, goes quickly; opts.look goes and looks at every cell instead. opts.order is "layer" (the default) or "column" (see the overview: cheaper for walls); a build carried on keeps the order it began with. A build saved before a re-zero (T.frameStale) is not carried on: T.build() says why and marks it stale, and a plan given starts afresh. The fuel watch counts the moves and stops the build, progress kept, when after 8 cells they come to over 3 times T.fuelFor's estimate for the cells so far: "circling: N fuel for M cells, estimate E"; opts.fuelWatch = false turns it off. opts: at ({ x, y, z }: build with the plan's anchor here), look, move (for T.moveTo; default { path = true, scan = false }), inside (a protected area the job owns), limit (the most cells to try in this run), restart, partial, retry, protect ("keep", true or an area name: protect the finished build under the plan's name, or that name; only when no cell failed), order, fuelWatch, player (false: no T.lint at the end), digBelow, temp and exit (for T.placeAt: a top slab on a floor is placed from where the floor is, dug and put back, only with digBelow; a cell that would cut the way to exit is refused). Info is { name, done, total, failed = list of { n, x, y, z, item, why }, placed (cells put in this run), there (cells found already in place), finished, resumed, protected, short, order, fuel = { spent, estimate, perCell }, warnings, previous, sealed (a line for each placement that closed the turtle in: T.placeAt's warning; opts.exit refuses those instead, each cell failing with why) }. Once every cell has been tried, the plan is put through T.lint (what stops a two-tall player): its warnings are info.warnings (each tagged where = "plan" or "around"); the plan's own are printed, a line a rule ("player: headroom at 3,1,4: ..."), and those round it (terrain, other buildings) as one count ("player: 4 more round it"); they never change the result.

T.verify(plan, opts)

    `plan` is a plan; nil checks the saved build. Every cell the plan does not leave alone is compared: the block's name, and each key of the state the plan names. A cell with a state to match, or that the map has never seen, is looked at with T.inspectAll (opts.inspect = "all" looks at every cell); the rest is read from the map, which the build keeps right. A cell that could not be looked at is listed too, with unverified = true. An empty list means the build is as planned. opts: at ({ x, y, z }), scan (true: scan the box with T.scanBox first), inspect, move (for the walking), inside, player (true: T.lint the plan's box of the map as well, after the look, for what stops a two-tall player: its warnings are info.warnings, and why it couldn't info.playerWhy).

== Swapping blocks ==

T.replace(box, pattern, item, opts)
    Swap every block in a box whose name matches a glob for another block: how many, and what could not be. Returns true, info; false, why, info when some were trapped or failed; nil, why when it couldn't begin.

    The box is six numbers in a table, or { x1 =, ... }; the glob matches block names (the namespace may be left out); `item` is the block to put in, with a state in brackets if it has one. The cells are those the map holds (opts.scan scans the box first, which the map needs to know it). Each is taken from the nearest free side the map shows, nearest next: the turtle looks at the block (one that has changed since is left), digs it and places the new one. A block with no free side (every neighbour solid in the map) is listed in `trapped` and never dug to, unless opts.digBelow: then (for a plain block) a neighbour with air over it is dug, stood in, the block swapped from there, and the neighbour put back from above with the same block (one that digging gives back, T.dropsItself, or one carried). Info is { replaced, same, trapped, failed, gone, more, via (swapped by way of a neighbour) }, trapped and failed being lists of { x, y, z, name, why }. opts: scan, limit (cells at most, default 1000), move (for T.moveTo), inside (a protected area the job owns, to swap blocks in it), partial, digBelow.

tl.craft: crafting and smelting: recipes as data, T.craft, T.craftBatch, T.canCraft, T.smelt, what burns and smelts

Loaded by turtlelib the first time one of its functions is used (T.craft, T.craftBatch, T.craftPlan, T.canCraft, T.recipe, T.addRecipe, T.smelt, T.smeltAt, T.fuelTicks, T.smeltsTo).

Recipes are written as the game's data packs write them: up to three rows of letters (a dot is an empty cell), what each letter stands for (a name, a list of names or a glob like "*_planks", minecraft: assumed), what comes out and how many.  A family is one entry: "minecraft:{}_stairs" over a list of blocks makes every one's stairs, the {} being the block's name without its ending (oak_planks gives oak, stone_bricks gives stone_brick); a map entry gives the block each result is made from (chiseled forms from their slabs).  A block of nine (coal, iron, gold, copper, redstone, lapis, emerald, diamond, bone meal and the rest, nuggets into ingots) is made both ways: nine into the block, the block back into nine.  T.addRecipe adds more, for modded items.  The table is T.RECIPES (it exists once this module has loaded), the newest first.

A turtle crafts through the crafting table as a peripheral, and only when every slot outside the grid is empty.  So T.craft works from a chest: it checks the chest has room for the whole inventory, puts the crafting table on (through T.withPeripheral: a chunk controller stays on), stashes everything in the chest, the pickaxe too, pulls each round's ingredients into the grid's slots (1-3, 5-7 and 9-11), crafts, stashes again, and at the end puts the inventory back and the product with it.  What it made is never junk (T.markCrafted).  T.canCraft says what is short, from the inventory and the chest.  A craft does the recipe asked for; an ingredient that is itself crafted (planks from logs, sticks from planks) is made first with its own T.craft, or in the same T.craftBatch: that stashes the inventory once for a list of recipes, each product going back in the chest for the next to use, and puts the inventory back at the end (T.craft is a batch of one that takes its product aboard).  T.craftPlan works the whole tree out first (torches need sticks, sticks planks, planks logs) against the inventory and the chests: the steps, the base materials, what is short; T.craftBatch takes the plan.

T.smelt runs a furnace: a furnace takes fuel through its sides, the item through its top, and gives the result through its underside only.  It sets the furnace up in front of the turtle, one block up, so the cell under it is free to stand in, drops the fuel from beside, the item from above, sucks the results from below as they cook (ten seconds an item), and takes the furnace back.  T.smeltAt does the same at a furnace standing in the world (fuel from a side, the item from the top, the results from below), and need not wait for it.  What burns and how long (T.fuelTicks; the nether's woods do not) and what smelts into what (T.smeltsTo) are tables: T.FURNACE_FUEL and T.SMELTS.

== Reading and adding recipes, and asking what is short ==

T.addRecipe(spec)
    Add a recipe (modded items, say): out (the item made), count, shape, key, mixed, and for a family of, from or map. True, or nil and why not.

    spec = { out = "mod:widget", count = 2, shape = { "AA", "B." }, key = { A = "minecraft:iron_ingot", B = "*_planks" } }. A letter in the shape is a name, a list of names or a glob (a name with no namespace is minecraft:'s); a dot is an empty cell; mixed = true lets one letter stand for different items (any planks). A family has out with {} in it and of = "X" for the letter that is the block, with from = a list of blocks, or map = { result = block }. The newest recipe is tried first. Kept in memory only: put the calls in /claude/helpers.lua to have them each session.

T.recipe(name)
    The first recipe that makes an item: { out, count, shape, key, mixed } or nil and why.

    shape is the rows of letters, key what each letter is (a name, a glob, a list of names; for a family the block this item is made from), mixed whether one letter may be several items. There may be more than one recipe for it; this is the first (the newest added, else the built-in).

T.canCraft(name, n, opts)
    Can the item be crafted: true, or false, why and the short list. Counts the inventory and the chest.

    name is the item, n how many to have (default 1; whole crafts, so more may come out). The chest is the container opts.chest names (front, top or bottom) or the first there is; nothing moves. Returns true and { crafts, makes }; or false, a sentence ("short of oak_planks: need 6, have 4") and the list of { item, need, have, short }. It does the one recipe asked for: an ingredient that is itself crafted, planks from logs, counts as short.

== Planning ==

T.craftPlan(targets, opts)
    Plan crafting { [name] = n } down the recipe tree against the inventory and the chests: { steps, base, short, ok }, and why when short; nil, why. T.prepare{ need = plan.base } fetches it, T.craftBatch(plan) crafts it.

    `targets` is { [name] = n } or { { name, n }, ... }. The tree is followed down (torches need sticks and coal, sticks planks, planks logs) against what the inventory and the chests T.catalogue has read hold (opts.chest, a side: the inventory and that chest instead; opts.stock: counts by name to plan with): what there is is used first, what isn't is made, and what can't be made is short. The targets themselves are made, not taken from what there is. Smelting is not planned: charcoal or glass that isn't there is short. The plan is { targets, steps = { { name, n, crafts } } in the order to make them, base = { name = n } (what to have at the chest: T.prepare{ need = plan.base } fetches it), short = { name = n } (a name, or what would do: "coal or charcoal", "*_planks"), ok }.

== Crafting from a chest ==

T.craft(name, n, opts)
    Craft n of an item from a chest (stash the inventory, fill the grid, craft, put it all back): true and how many, or false/nil and why.

    It works from a chest: the container in front, above or below, or opts.chest (a side, or { x, y, z, side } to walk to), else the junk chest. The chest needs room for the whole inventory; that is checked first, and so are the ingredients (inventory plus chest) and a crafting table (on board, equipped or in the chest). Then the table goes on (a chunk controller stays on), everything is stashed in the chest, the grid is filled from it and crafted, round after round, and the inventory comes back with the product. n is rounded up to whole crafts. opts: chest, partial (craft what the ingredients allow), move (for T.moveTo).

    Returns true, made; or false, why, made (it made some, or could not carry them); or nil, why (nothing was touched): no recipe, short of an ingredient (the third value is the list from T.canCraft), no chest, no room in the chest, no crafting table. What it made is marked as crafted, so T.isJunk never says it is junk. A chest T.addChest knows is read again after (T.recount), so the chests' list says what the craft took and left.

T.craftBatch(list, opts)
    Craft a list { { name, n }, ... } (only what it names) or a T.craftPlan plan (sticks for torches too) with one stash, the products left in the chest (opts.take: aboard): true, info; false, why, info if some failed; nil, why.

    The list is in the order to make them, each as T.craft takes it (n rounded up to whole crafts); a plan is its steps (one that is short is refused unless opts.partial). It works from a chest as T.craft does (the same opts.chest, and the junk chest by default), but stashes the inventory only once: the tools go in too, the crafting table goes on, and each recipe's ingredients come from the chest into the grid, are crafted, and the product goes back in the chest, where the next recipe can use it (planks, then sticks, then torches). At the end the inventory comes back as it was; the products stay in the chest unless opts.take (true: what was asked for, a plan's targets; or a name, list or set of names) brings them aboard. A recipe that can't be made is noted and the rest go on. opts: chest, take, partial (craft what the ingredients allow), move. Info is { crafted = { name = n }, failed = { { name, n, why } }, taken = { name = n }, left = { name = n } (made, but it stayed in the chest: the why says why), used = { name = n } (made, then used by a later recipe: not owed to opts.take) }. A chest T.addChest knows is read again after (T.recount).

== Fuel and smelting ==

T.fuelTicks(name)
    How many ticks a furnace burns the item for (20 a second; it smelts an item in 200), or nil if it is not a fuel.

    Coal and charcoal 1600, a block of coal 16000, a lava bucket 20000, planks, logs and wooden things 300 or less. The nether's woods (crimson and warped stems, planks and the rest) do not burn. The table is T.FURNACE_FUEL.

T.smeltsTo(name)
    What the item smelts into in a furnace, or nil if it does not smelt.

    Ores and raw metals to ingots, cobblestone to stone, sand to glass, clay to bricks, logs to charcoal (not the nether's stems), raw food to cooked. The table is T.SMELTS.

T.smelt(item, n, fuel, opts)
    Smelt n of an item in a furnace the turtle carries, set up in front of it: true and how many came out, or false/nil and why.

    The furnace goes up in front of the turtle, one block above it, so the cell under it is free to stand in. Five cells must be free: the two over the turtle, the one in front of it, and the two over that (where the furnace stands and above it); opts.move = { dig = true } lets it dig them (opts.move is for T.moveTo). Fuel goes in from beside, the item from above, and the results are sucked from below as they cook (ten seconds an item, at most 64 at a time); then the furnace is taken back (in a protected area too: it is the turtle's own) and the turtle comes home, facing as before. fuel is an item name (default: charcoal, coal, then planks or logs, whichever there is enough of). What it makes is marked as crafted.

    Returns true, got; false, why, got (it did not all come out in time); or nil, why (nothing started): not smeltable, short of the item or the fuel, not a fuel, no furnace on board.

T.smeltAt(cell, item, n, opts)
    Smelt n at a furnace standing at cell {x, y, z}: fuel in from a side, the item from the top, the results from below. True, got (true, 0, info with opts.wait = false: n = 0 fetches them later); false, why, got; nil, why.

    `cell` is the furnace's { x, y, z }. The fuel goes in from a side (from below if no side can be reached), the item from the top, and the results are taken from below, so the cells over and under it must be free. n is how many (1 to 64), or 0 to only take out what has cooked. It waits for them (ten seconds an item) unless opts.wait = false: then it loads the furnace and returns at once (info.ready is the seconds it takes), and T.smeltAt(cell, item, 0) fetches them later. opts: fuel (a name, as T.smelt's; false: put none in, it has some), stay (don't go back to where it began), move (for T.moveTo; default { path = true, scan = false }). What comes out is marked as crafted.

tl.harvest: taking blocks by name, fuel from lava, and what a job will cost in fuel

Loaded by turtlelib the first time one of its functions is used (T.harvest, T.refuelFromLava, T.fuelFor).

T.harvest digs every block in a place whose name matches a glob, nearest first, but a block only after the matching blocks above it in its column (top down), and never one with a falling block (sand, gravel, concrete powder, an anvil) over it that is not itself to be dug: digging out from under it would bring it down.  A block that lava or a water source touches beside it or over it (T.liquidNear) is left (opts.liquid lifts that), so is one in a protected area (opts.inside names the area the job owns) and a chest or a computer (T.cfg.digContainers).  It counts as it goes and stops at the target.  The place is a box in the turtle's frame (the map is scanned for it as needed), a scan's result (T.scan's { ["x,y,z"] = name }) or a list of cells such as T.map.find gives.  Each block is dug from the nearest cell next to it that the map shows free, tunnelling to one when opts.move allows digging.  The turtle stays where the last block was.

T.refuelFromLava finds the nearest lava source the map knows, goes next to it, takes it up with an empty bucket (a turtle that places an empty bucket on a source takes it up, as mine's scoop does), burns the bucket of lava for 1000 fuel and goes back where it began.

T.fuelFor adds up what a route, a build and some scans will cost in fuel and says whether the tank and the fuel on board will do.  A scan of radius 8 or less costs nothing (the Geo Scanner's free radius by default); a wider one is an estimate (set T.cfg.scanFuel = { [12] = cost } from what T.scan reports in info.fuel).

== Harvesting ==

T.harvest(pattern, where, target, opts)
    Dig the blocks in a place matching a glob, nearest first, top down, leaving protected areas, ones liquid would flow in by and ones under sand. True, info; false, why, info when short; nil, why if it couldn't begin.

    `pattern` is a glob of block names (the namespace may be left out). `where` is a box in the turtle's frame (six numbers in a table, or x1 to z2 fields; the map is scanned for it if it does not know it all, unless opts.scan is false), the result of T.scan, or a list of cells ({ x, y, z }, as T.map.find gives). `target`, if given, is how many blocks to dig before stopping (opts.item, a glob of item names, counts the items of that kind that came aboard instead). Each block is looked at before it is dug and left if the map was wrong. Left alone, and listed in info.skipped with why: a block with a falling block over it that is not to be dug too, one that lava or a water source touches beside it or over it (T.liquidNear; opts.liquid, or opts.lava as before, digs those), one in a protected area (opts.inside names the area the job owns) and a chest or a computer (T.cfg.digContainers). A block with no free cell beside it is skipped unless opts.move lets it dig a way in, and so is one in opts.exclude (protected areas' names and boxes, as T.refuelFromLava takes). It stops when the inventory is full (T.cfg.autoDump keeps room), the fuel is out, it has spent opts.maxFuel fuel (scanning included) or run opts.timeout seconds (real ones, at any tick rate). Info is { got, target, items = { name = count aboard now that were not before }, seen, gone, skipped, failed, more, scanned, spent, stopped }, the lists of { x, y, z, name, why }, spent the fuel it used. opts: scan, limit (cells at most, default 1000), move (for T.moveTo, default { path = true, scan = false }), inside, liquid, item, exclude, maxFuel, timeout.

== Fuel from lava ==

T.refuelFromLava(target, opts)
    Fill the tank from lava the map knows: go to the nearest source, take it up with an empty bucket, burn it, and come back, facing as before. Returns true, fuel gained, info; false, why, fuel gained, info; nil, why.

    `target` is the fuel level to reach (default the tank's limit); it stops there, or when another bucket would not fit the tank (1000 each), or when no lava source is left to reach. It needs an empty bucket aboard (a lava bucket aboard is burned first). The lava comes from the map (T.scan puts it there), the nearest first; a cell is looked at before the bucket goes on it, and one that proves to be flowing, not a source, is passed over. Lava in a protected area is left (the area T.inside names is the job's), and so is lava in opts.exclude, a list of areas' names and boxes. opts.tries (default 20) is how many lava cells it will try, opts.move is T.moveTo's (default { path = true, scan = false }, never into lava). Info, once it has gone looking, is { tries = { { x, y, z, found } } }: each cell tried, in order, and what it found there ("taken", "flowing", "out of reach", "not lava (minecraft:air)", ...); when it comes back short, the why says what the tries that came to nothing found, and where.

== What a job costs in fuel ==

T.fuelFor(plan, opts)
    What a job will cost in fuel, against the tank and the fuel on board: true, info if it will do; false, why, info if short; nil, why for a plan it can't read. Moves nothing.

    `plan` is a table with any of: route (a list of points { x, y, z } to go through from here), go (one point), build (a blueprint, or its text), box and radius (a box to scan with T.scanBox), scans (a number of scans of `radius`, default 8), back (true: and return to where the turtle is now), extra (fuel to add). A plan that is a blueprint, or a bare list of points, is a build or a route. Moves cost a fuel each; those of a route and the way to a build are made 25% longer for detours (opts.detour), and T.cfg.fuelMargin (30) is added on top. Info is { route, build, scans, back, extra, margin, need, tank, board, have, enough, short }, the costs in fuel and `board` the fuel value of the T.fuel items aboard.

tl.journal: the job journal, the undo journal and reports to the player

Loaded by turtlelib the first time T.job, T.report, T.undo, T.undoMark or T.undoClear is used, or when T.cfg.undo is set.

The job journal (T.job) keeps a job in one data file, .job: the goal, the steps of the plan and which are done, notes, and the progress a build or a harvest reports as it goes.  A reset, a crash or a cleared conversation then carries on at the step:
    T.job.start("build the keep",
        { "clear the ground", "lay the floor", "raise the walls" })
    T.job.done()                  -- the next step is done
    local job = T.job.resume()    -- job.step is the text of the step to do now, job.done of job.total are done
T.build and T.harvest write their progress there (T.job.progress) when a job is on, and write nothing when there is none.

The undo journal (T.cfg.undo = true) writes down each block the turtle digs or places, in the data file .undo: the block's name and its state for a dig (the dig looks first, so the state comes free), the item for a placement.  T.undo(n) puts the last n back: a dug block is placed again (through T.placeAt when it has a state, with the item on hand) and a placed one is dug out.  T.undoMark() gives a mark to undo back to later: T.undo(nil, { since = mark }).  The journal is cut to its newest 2000 entries (the setting undo.max).  Moves are not written down, and neither is anything done while undoing.

T.report tells the player (the setting turtle.player, never in the code; everyone when it isn't set) through a chat box, with where the turtle is, its fuel and the job's progress added (not once the job is finished: its last step done).  A chat box that is not attached is equipped for the moment through T.withPeripheral; the chat box's cooldown is waited out and retried.  T.report.every(n) makes the job tell the player once in every n steps (a step is a T.job.done, or a progress line from a build or a harvest).  T.report.ask asks the player in chat and waits for an answer starting with "claude"; T.report.lastTold says when the player was last told anything.

== The job journal ==

T.job.start(goal, steps)
    Start a job: its goal and the steps of the plan (a list of texts, or none). Replaces the job that was on; it lasts until T.job.clear. True, or nil and why.

T.job.done(step)
    Mark a step done: its number, its text, or nothing for the next one not done. Returns true and how many steps are left, or nil and why (no job, no such step). The last step done finishes the job.

    A step done twice is done. A job with no steps is finished by T.job.done(). A finished job is left out of what T.report adds (T.job.status still says how it ended); T.job.start begins the next, T.job.clear forgets it. With T.report.every set, the player is told once in every n steps.

T.job.resume()
    The job as it stands: { goal, steps = { { text, done } }, step (the text of the step to do now), next (its number), done, total, finished, notes, work = { key = text }, every }; nil and why if there is none.

    This is what to call after a restart: the job is carried on at job.next.

T.job.note(said)
    Add a note to the job (the newest 40 are kept). True, or nil and why.

T.job.progress(key, said)
    Set the progress line for a key such as "build" or "harvest" (text nil takes it away). T.build and T.harvest call this when a job is on. True, or nil and why.

T.job.status()
    How the job stands in one line ("step 2 of 3: lay the floor; build keep: 40 of 300 cells"), or nil if there is none.

T.job.clear()
    End the job: forget it and its file (a finished job, its last step done, stays until then, out of the reports). True.

== Reports to the player ==

T.report.now(said, opts)
    Tell the player `said`, with where the turtle is, its fuel and the job's progress (until it is finished) added: true, or nil and why.

    The player is the setting turtle.player (opts.player overrides it); with none, it's said to everyone in the chat (ADR-0013 D3: what reports speaks to everyone unless turtle.player makes it private). A chat box on a side is used as it is; otherwise one aboard is equipped for the moment (T.withPeripheral), which puts back what was on that side. The chat box's cooldown is retried opts.tries times (default 5), opts.wait seconds apart (default 1). opts.plain sends the text alone. T.report(said, opts) does the same.

    opts.from names a side ("top", "bottom" or "front") whose container may hold the chat box: with none aboard or attached, one is taken out of it for the telling and put back after (a program that keeps its chat box in the chest at home).

T.report.try(said, opts)
    T.report.now for a program's end or trouble: the same arguments, but it never raises. True, or nil and why (Ctrl+T goes on).

T.report.ask(question, opts)
    Ask the player `question` in chat and wait for the answer: the text (the prefix taken off), the player who gave it and when (seconds since 1970); or nil and why ("no answer in 300 s", no chat box).

    The question goes to the setting turtle.player (opts.player overrides it), or to everyone when none is set, through a chat box as T.report's does: one on a side as it is, else one aboard equipped for the wait (T.withPeripheral) and put back after. An answer is a chat message starting with opts.prefix (default "claude": "claude yes" or "claude: yes"), from that player only (anyone's with none set). opts.timeout is the longest wait in seconds (default 300); opts.remind says the question again every so many seconds (default never). Ctrl+T stops the wait. The other chat messages it reads go to T.hooks.heard, when it is set (claude passes the player's on to the model).

T.report.lastTold()
    When the player was last told something through T.report, T.report.now or T.report.ask: seconds since 1970, or nil if nothing has been told since the computer started.

    claude reminds the model to keep the player told by it (the setting claude.remindChat).

T.report.every(n)
    Make the job tell the player once in every n steps (a T.job.done, or a progress line from a build or a harvest); 0 or nil turns it off. It is kept in the job, so it needs one (T.job.start) and lasts a restart. True, or nil and why.

== The undo journal ==

T.undoMark()
    The mark of the journal as it is now: T.undo(nil, { since = mark }) undoes everything done after it.

T.undoClear()
    Empty the undo journal. True.

T.undo(n, opts)
    Put back what the journal wrote down, newest first: the last n entries (default 1), or those after opts.since (T.undoMark). Returns true, info; false, why, info when some could not be; nil, why if there is nothing to undo.

    A block that was dug is placed again (T.placeAt when it had a state, so it faces as it did; the item must be aboard); one that was placed is dug out if it is still there. The turtle goes next to each cell (opts.move is T.moveTo's; opts.inside names a protected area the job may work in). An entry that was done leaves the journal; one that could not stays, and info.failed lists it: { seq, kind, x, y, z, name, why }. An entry written before a re-zero (T.frameStale) is not undone: it fails, saying why, and stays marked stale. info.undone is how many went. It does nothing to what the turtle did since to those cells except as said, and it writes nothing to the journal itself.

tl.light: block light over the map, and the cells where a mob could spawn in the dark

Loaded by turtlelib the first time T.light or T.darkCells is used.  Cells are the turtle's own (the frame it counts in).

A flood fill of block light over the map (tl.world), as the game spreads it: a light gives its level in its own cell, and each step to a side, up or down loses 1, so a torch (14) lights the cells beside it to 13 and nothing 14 steps away.  What light goes through comes from the lint's kinds (T.blockKind): what a player passes through, railings, lanterns, stairs and slabs; a solid block stops it unless the table of exceptions says it is clear (glass, leaves, ice, a chest, a plant).  A slab or a stair lets light through sideways but not through its full face (a bottom one's underside, a top one's top); one whose half the map lacks is taken as a bottom one.  Lights up to 14 cells outside the box count (the box is grown by 14 to look for them), and so does light that goes round a wall outside the box. A cell the map never saw stops light.  Sky light isn't modelled: the dark cells are those of a roofed place, or of any place at night.

A monster spawns with its feet in a cell with room (that cell and the one over it: nothing it collides with, so air, a torch or a sign, but not a rail, a carpet, a pressure plate, a button, a lever or redstone, which stop spawning) over a floor with a full, sturdy top (a solid block, a top slab, an upside-down stair; not a bottom slab, glass, leaves, ice, a block that isn't a full one such as a chest or farmland, or one giving light 14 or more such as glowstone), when the block light in its feet cell is at or under the dimension's limit (Java 1.21.1's code, checked 2026-11-17):
  overworld, end
      0 (the dimension's monster_spawn_block_light_limit)
  nether
      7 for skeletons, wither skeletons and endermen (monster_spawn_light_level); 11 for zombified piglins, piglins, hoglins and blazes (the walk-target check every pathfinding monster passes, MC-156004); ghasts and magma cubes whatever the light: only the floor or the room stops them
The turtle can't tell which dimension it is in: opts.dimension says, else the setting T.cfg.dimension, else it is the overworld.  Only two cells of room are asked for (an enderman wants three, a ghast more, a spider a wider space), and the game's chances (sky light at night, the distance from a player) aren't modelled.  Mods in a pack can change spawning, and a block the tables don't know is taken as a solid one: check in game, comparing the dark cells with where mobs appeared.

== tl.light: block light over the map, and the cells where a mob could spawn in the dark ==

T.light(box, opts)
    The block light in a box from the map: a function level(x, y, z) giving a cell's light (0 to 15; nil for a cell outside the box), and info; nil and why.

    `box` is { x1, y1, z1, x2, y2, z2 } (or the fields), 65536 cells at most. Lights up to 14 cells outside it count; what light passes and what stops it is in the overview (a cell the map never saw stops it). opts.with = a list of { x, y, z, name, state } read in place of the map's cells: what a torch there would do ({ 3, 1, 4, "torch" }), or a light taken away ({ 3, 1, 4, "air" }). Info is { cells, sources (the lights that reached the grown box), guessed (lights whose level goes by a state the map lacks, such as a redstone lamp's lit: the game's default taken), cut (more than 20000 lights: some left out) }. Block light only, as the game spreads it in Java 1.21.1: check in game.

T.darkCells(box, opts)
    Where a mob could spawn in a box: a list of { x, y, z, light } (the feet cell) at or under the dimension's limit, darkest first, opts.limit at most (50; info.more the rest), and info (info.unsure: cells to inspect); nil and why.

    A cell is spawnable with room for a mob (it and the cell over it: air, a torch, a sign; not a rail, carpet, button, pressure plate or redstone) over a full, sturdy floor (a solid block, a top slab, an upside-down stair; not a bottom slab, glass, leaves, ice, glowstone or a block that isn't a full one). The limit (see the overview): the overworld's and the end's 0; the nether's 11, in two groups, light 7 or less (skeletons, wither skeletons, endermen) and 11 or less (zombified piglins, piglins, hoglins, blazes), and the spawnable cells lit over it listed apart in info.anyLight, since ghasts and magma cubes spawn whatever the light (only a slab or glass floor, or no room, stops them). opts: dimension ("overworld", "nether", "end"; else the setting T.cfg.dimension, else the overworld: the turtle can't tell), max (the limit, overriding the dimension's), limit (cells listed, default 50), with (as T.light). Info is { dimension, max, spawnable (cells), dark (cells at or under the limit), more (past the limit), groups (a list of { max, mobs, count }), anyLight and anyLightCount (the nether), unsure (a list of the cells, { x, y, z }, over a slab or stair whose half the map lacks, taken as a bottom one: inspect them, since a top one is a floor), unseen (cells of the box the map never saw), sources, guessed, cut (as T.light), summary (a line, which says "listed the darkest N of M" when the list is cut) }. Mods can change spawning: check in game.

T.planLights(cells, candidates, opts)
    The fewest lights, of the places given, that bring every cell to opts.min (8; 12 in the nether): a list of { x, y, z, name } to place, nearest first, and info; nil and why.

    `cells` are the cells to light ({ x, y, z }: a walkway's feet cells, T.darkCells' list); `candidates` the cells a light may go in ({ x, y, z } or { x, y, z, name }: in the wall beside a path, the floor under it). It reads the map and T.light's model (what passes light and what stops it, the lights already there): a cell already at opts.min is done; then, again and again, the candidate that brings the most cells still dark to opts.min is taken (a greedy cover: few lights, not always the fewest), until all are lit or no candidate helps. The light is opts.item (default minecraft:lantern, 15; a torch 14, glowstone 15, a soul lantern 10), or a candidate's own name. opts: min, item, dimension (the default min: T.cfg.dimension, else the overworld). Info is { lit (already at min), covered (by the lights chosen), left (a list of the cells no candidate reaches), lights, summary }. Nothing is placed: T.placeAt them (a lantern's opts.hanging, a torch on a wall) and T.darkCells to check.

tl.lint: a build as a two-tall player meets it: warnings about its stairs, railings, drops and lights, and paths

Loaded by turtlelib the first time T.lint or T.walkable is used.  Cells are the turtle's own (the frame it counts in).

The turtle is one block tall and the player two (1.8, stepping up a block at most), so a build the turtle gets round can still stop a player.  T.lint reads a build from the map, or a plan's own cells with the map round them, and warns; it never refuses, since a player's own design may break a rule on purpose.  The rules:
  headroom
      a stair walked up needs 3 air above it: the body rises half a block onto the next step while the head is still over this one (the top stair of a flight needs only 2 when the way off it is level)
  approach
      the cell in front of a flight's first stair needs a floor and 3 air (the step up starts there)
  exit
      the cell beyond a flight's last stair needs a floor at the stair's top and 2 air: not a wall, not an edge
  railing
      two railings (fences, walls, panes, bars, gates) that meet only on a diagonal, level or a block apart in height, don't join: a player slips between them; a railing or a block in either cell between closes it
  drop
      a walk cell (2 air over a floor) with an open side over a drop of more than 3, and no railing there
  lantern
      a lantern at head height over a walk cell: a player walks into it
  light
      a torch on a wall (soul and redstone too) in a walk cell's feet or head cell: it sticks into the way (a lantern at head height is the lantern rule's); glowstone or a shroomlight set flush, or a torch on a merlon or the wall's top, lights it as well
A stair goes by its state (facing, half), which the map has only for blocks that were inspected (T.inspectAll, T.verify; a scan gives names alone), and its compass facing needs the world origin: a stair without them is counted as unchecked and only its headroom is looked at.  A lone stair that climbs to nothing (a seat against a wall, a bench of stairs side by side) isn't a flight, and none of the stair rules is looked at for it.  A cell the map has never seen breaks no rule.

T.walkable searches the map for a way a player walks from one cell to another (breadth first: fewest steps).  A player's place is the cell its feet are in, over a block to stand on (or on a ladder), and its height in half blocks (a bottom slab is half a block, a fence or wall one and a half).  A step goes to a side, up a block at most (a stair or a slab is a step like any other) or down any height; a climb goes up or down a ladder.  The body is 1.8 high, so a step up needs 3 air where it starts as well as 2 where it ends (the reason a stair needs 3 air).  Lava and fire are never walked into, water breaks a fall, and a fall over 3 is taken only when there is no way without one, and listed.

== tl.lint: a build as a two-tall player meets it: warnings about its stairs, railings, drops and lights, and paths ==

T.blockKind(name)
    What a block is to a player, by its name: the kind's name (open, railing, stairs, slab, solid, ...) and a copy of its facts ({ pass, floor, height, ... }).

    The kinds are open, ladder, water, hot, gate, railing, lantern, walltorch, stairs, slab and solid (a name no rule knows). The facts: pass (the body goes through it), floor (a player stands on it), height (its top in half blocks), climb, soft, hot, rail, lantern, light, stairs, slab. The lint and T.walkable go by these; tl.light reads light's way through a block from them.

== The lint ==

T.lint(what, opts)
    What stops a two-tall player in a build (a box or a plan), read-only: headroom, a flight's approach and exit, diagonal railings, drops over 3, lights in the way. A list of { rule, x, y, z, text }, and info (info.rules; opts.rules).

    `what` is a box of the map ({ x1, y1, z1, x2, y2, z2 }, or the fields) or a plan (as T.build takes one: its own cells and states, the map for the cells it leaves alone and round it). The cells looked at are the box's and, for walking on its top, the layer over it; the cells round them (an approach, a drop) are read too. A warning is { rule, x, y, z, text }: rule is headroom, approach, exit, railing, drop, lantern or light (see the overview), x, y, z the cell (the stair, the railing or the walk cell), text says it in plain words with the cells involved. Warnings, not refusals: a design may break a rule on purpose. Nil and why if it can't start. Info is { cells, unchecked (stairs with no facing in the map or no origin: only their headroom looked at), more (warnings past opts.limit, default 50), rules (a count by rule), summary (a line a rule: its first warning, and how many more) }. opts.rules (a list of rule names) checks only those. The limit is shared: the list takes each rule's first, then each one's second, and so on, so one rule with many can't crowd out the others. For a plan, each warning is tagged where = "plan" when its cell, the floor under its walk cell or a cell it names is one of the plan's, else "around" (terrain and buildings round it); the plan's come first, and info adds inPlan and around (the counts) and planSummary (the summary of the plan's own). T.build prints only those, and a count of the rest.

== Walking ==

T.walkable(from, to, opts)
    A way a two-tall player walks from one feet cell to another over the map (steps up 1, ladders, falls over 3 only if there's no other way): the path (feet cells after `from`, the last `to`) and { falls }; nil and why if none.

    `from` and `to` are cells ({ x, y, z } or { x =, y =, z = }) a player's feet are in: the cell over the block stood on. A player steps to a side, up a block at most (stairs and slabs included) or down, and climbs ladders; a step up needs 3 air where it starts (see the overview). Falls over 3 are taken only when there is no way without one, and listed; opts.maxFall refuses those over it. The why of no walk names what shuts the ways nearest the goal (a block in the way, a step too high, headroom, a fall, cells the map hasn't seen). Info is { nodes (places searched), falls = list of { x, y, z, height } (where each fall over 3 lands) }. opts: maxFall, limit (places to search, default 20000), margin (how far outside the box of the two cells, default 16), with (a list of { x, y, z, name, state } read in place of the map's cells, as T.light takes it: would a player still get through with a lantern here, or once this wall is gone?).

tl.path: routes: a search over the map for a way to a cell, and walking it

Loaded by turtlelib the first time T.path or T.travel is used (T.moveTo asks for T.travel when a straight run is blocked and opts.path is set).  Cells are the turtle's own (the frame it counts in).

T.path finds a route: A* in three dimensions over the map (tl.world), with a binary heap.  What a step into a cell costs depends on what the map holds there:
  known air or water
      one move
  a block it may dig
      a move and a dig (opts.dig says what may be dug, as for T.moveTo), unless lava or a water source is beside it or over it (T.liquidNear): that is a wall unless opts.liquid
  a cell never seen
      a move and a dig when digging everything is allowed; otherwise a move and a penalty, so a route through the unseen is possible but the known is preferred (it is checked as it is walked)
  a wall
      never: a cell of a protected area the map doesn't know to be empty (a block, or never seen: nothing in an area is dug, except in the one opts.inside names; its known air and water are crossed like any other), a block beside liquid (above), what opts.avoid lists (lava, fire, doors and the player's furnishings: ladders, trapdoors, fence gates, signs, lanterns, torches, rails; unless it says otherwise), a block it may not dig (a chest, bedrock, a nether portal, anything opts.dig leaves out), and any cell in opts.avoidCells
The search reads the map's cubes as strings (string.byte), not as tables of cells, so a big search stays cheap in memory; it gives the rest of the computer a turn about every half second (CC stops code that goes seven seconds without yielding), and gives up past a limit of cells searched, saying so; when it gives up, or every way is walled off, it names the protected areas and the avoided blocks (doors, lava, ladders, ...) it met, which no longer search gets through. When the player's furnishings were among them (the default avoid list only), it searches once more, the same limit, with only the hazards (lava, fire, doors) avoided and the furnishings open to a dig; a way found is named, not taken: "a way exists through minecraft:wall_torch at x,y,z (lift it and put it back)". Before it searches, a small flood from the goal (1024 cells at most) looks for a way out: a goal walled in (a room of doors, a protected box) fails at once, "the goal is walled in by" what walls it, not after the whole limit.  Only the protected areas that overlap the search's box are tested for each cell.

T.travel goes there.  From the map it looks for a clear layer, a height at which the whole way is known to be empty, between the highest floor and the lowest ceiling on the way (the Nether has a roof: a fixed height hits bastion ceilings): up, across, down.  If the map doesn't know enough it scans the route's box first; if there is no layer it uses the search.  Then it walks the route.  A block it didn't expect stops a step: it notes the block in the map and plans again from where it is, a few times.

== The search ==

T.path(x, y, z, opts)
    A route to the cell x, y, z through the map: a list of cells to step into, one after another, the last being the goal (empty when already there); nil and why if there is none.

    It starts from where the turtle is (opts.from = { x, y, z } to plan from elsewhere). The costs and the walls are in the overview of this module. A second result gives { nodes, cost, digs, unknown, areas }: how many cells the search looked at, the route's cost, how many of its cells need a dig or were never seen, and how many protected areas overlap the search (the only ones it tests). A goal walled in fails at once: "the goal ... is walled in by ...". When the player's furnishings were in the way (with the default avoid list), the why says where a way would go through them, up to 3 cells: "a way exists through minecraft:wall_torch at x,y,z (lift it and put it back)". Nothing moves. opts (all optional):
      dig        false (default), true, a glob, or a list or set of globs: what a route may dig (as for T.moveTo)
      digOnly    a list or set of cells (T.cellSet): the only cells a route may dig
      avoid      a glob, a list or a set: blocks a route stays out of (default: lava, fire, doors and furnishings, as
                 T.moveTo; {} avoids nothing)
      inside     the name of a protected area the route may dig in, or a list (and those of T.cfg.inside, see T.inside)
      liquid     true: a block with lava or a water source beside it or over it may be dug (by default it is a wall)
      avoidCells a list of { x, y, z } cells a route may not use
      limit      cells to search before giving up (default 20000)
      margin     how far outside the box of the two cells it may look (default 24)

== Walking a route ==

T.travel(x, y, z, opts)
    Go to the cell x, y, z by the map: along a clear layer if there is one, else by a search; true (and T.moveTo's warning, if it dug under sand or gravel), or false and why.

    Up, across and down at a height where the map shows the whole way empty (the lowest climb first); if the map doesn't know enough to find one it scans the route's box first (T.scanBox, once; opts.scan = false skips that); with no layer, T.path's search. Each stretch is walked with T.moveTo. A block it did not expect stops a step: the block is noted in the map, the cell is kept out of the next plan, and it plans again from where it is, up to opts.replans times (default 6); a dig it refuses for the liquid beside it (T.moveTo's opts.liquid) is planned round so too. opts are T.path's (dig, digOnly, avoid, inside, liquid, avoidCells, limit, margin), plus span (how far above the higher end a layer may be, default 8), scan, replans, and scanning's opts.move. On failure the turtle stays where it got to. A target too far for the search (it gives up at its limit) is gone to in legs of about 16 blocks, a scan (radius 8, no fuel) at each, the second result saying it hopped; opts.maxFuel caps what the legs spend, opts.hops = false doesn't hop.

tl.place: placing blocks the right way round: stairs, slabs, logs, torches, doors and the rest, and lighting a fire

Loaded by turtlelib the first time T.placeAt or T.ignite is used.  Cells are the turtle's own (the frame it counts in).

A turtle does not choose how a block lands.  What it gets depends on how the turtle places it, because the game has the turtle's fake player click a block, and the block's state comes from the click (CC:Tweaked's TurtlePlaceCommand, and Minecraft's rules for each block).  The game tries, in order: a block already in the target cell, the block BEYOND the target (clicked on the face toward the turtle), for a sideways place the block under the target (clicked on its top), and last the turtle's own block.  A sideways click lands just below the middle of a face, so what that gives is, in short:
  sideways
      stairs and slabs bottom half, the stair facing the turtle's heading; a log lying along the heading with a block beyond (standing with only a floor); a torch, sign, ladder, button or lever hung on the block beyond; a door, gate or chest facing as the turtle does; a piston, dispenser or dropper facing back at the turtle (an observer away from it), up onto a floor (an observer down); a repeater or comparator, on a floor, facing back at the turtle
  placeDown
      stairs and slabs bottom half if there is a block under the target, else top half; a piston up onto a block, else down (an observer the other way)
  placeUp
      stairs and slabs top half if there is a block over the target, else bottom half; a piston down onto a block, else up (an observer the other way)
  (from above or below a ladder hangs on the block beside the target the way the turtle faces)
(With nothing to click but the turtle's own block, a sideways stair faces back at the turtle.) The table of what each approach yields is data (T.PLACE_TABLE): per family of block, per approach (front, down, up), rows that say "if there is a block beyond (or a floor under the target), these state values".  A row's value is a plain word (half=bottom) or relative to the turtle's heading: facing=heading, back, right or left, and axis=along (the heading's) or across.  The rest of this comment is how it is used.

T.placeAt(x, y, z, item, { facing, half, axis }) works out which approaches the table says give that state and the map (tl.world) says are possible, goes to the nearest, places, inspects, and if the state came out wrong digs the block and tries the next.  Facing is a compass name, so it needs the world origin (T.setOrigin: the compass way the turtle's frame points); half and axis do not, nor a piston's or observer's facing up or down.  Where the map does not know what is beside the target the approaches are only guesses and go last.  What actually came out is remembered per family, in the data file .placements, but only when the map knew every fact the row depended on: a table row that was wrong is corrected once, for every later placement.  A door goes in after the walls round it, and needs a solid block under it and the cell above free; T.ignite lights a fire from above with flint and steel.  A sign takes its text (opts.text), which the game writes when the turtle places it, and opts.toward turns it to a reader (T.signFor finds the cell in front of one).

== Looking at what came out, and taking it back ==

T.forgetPlacements(family)
    Forget what T.placeAt has learnt (the data file .placements), for one family ("stairs", "slab", "torch", ... as T.placeInfo names them) or for all. True, or false and why.

    A wrong row learnt (say from a block the map had wrong) is laid over the table from then on; this puts the table's rows back.

== Support ==

T.dropsItself(name)
    Does digging the block give the block back (planks, bricks, a log: yes; stone, grass, glowstone: no)? The list placeAt's opts.digBelow and T.replace's go by to put a dug floor back; a block it doesn't know is a no.

== Placing a block with the state wanted ==

T.itemOfBlock(name)
    The item that places the block `name`: "minecraft:redstone" for "minecraft:redstone_wire", "minecraft:torch" for a wall_torch, a crop's seeds; any other block's name as it is.

    Covers the vanilla 1.21 blocks whose item has another name: redstone dust, tripwire (string), the wall forms of torches, signs, hanging signs, banners, heads and skulls and coral fans, crops and stems, cocoa, sweet berries, glow berries, and the grown parts of kelp, vines and big dripleaf (not what a bucket places). T.placeAt takes the block it finds as the item's by it, and a plan (tl.blueprint) names the item.

T.blockOfItem(item, form)
    The block the item `item` places ("minecraft:redstone_wire" for "minecraft:redstone", else the item's own name), or with form "wall" the one it makes hung on a block's side (a wall_torch for a torch), nil if none.

    The other way round from T.itemOfBlock. The wall forms are those of torches, signs, hanging signs, banners, heads and skulls, and coral fans ("minecraft:oak_wall_sign" for an oak_sign).

T.placeInfo(item)
    What placeAt can place this item by: { family, keys, hang, door }, or nil if the item is not a block it knows.

    family is stairs, slab, log, chain, torch, lantern, sign, ladder, button, door, trapdoor, fence_gate, chest, piston (and dispenser and dropper), observer, diode (a repeater or comparator), fence, pane, wall or block; keys is the set of state names placeAt can be asked for with it (facing, half, type, axis, face, rotation, hanging: a slab takes half and type, which are the same); hang is true for a family that hangs or stands on a solid block (a torch, lantern or standing sign stands on the post of a fence, a wall, a pane or a chain too, though nothing hangs on their sides; a lantern hangs under one, opts.hanging); door is true for a family of two blocks. Used by tl.blueprint to order the work and to ask for only the states that can be asked for.

T.placeAt(x, y, z, item, opts)
    Place item at the cell x, y, z with the state wanted (opts.facing, half, axis, hanging; a sign's opts.text; opts.digBelow lets it dig a floor to stand in and put it back): the block, its state and how; nil and why if it can't.

    It works out from the table which approaches (placing sideways, from above or from below, from each side) give the state wanted and the map says are possible, goes to the nearest with T.moveTo, places, inspects, and if the state is wrong digs the block and tries the next approach, learning what the game actually gave (see the overview). opts.facing is a compass name (north, east, south, west) and needs the world origin (up or down too for a piston, dispenser, dropper or observer, which need none; a repeater or comparator stands on a block); opts.half is bottom or top for a stair, slab or trapdoor; opts.axis is x, y or z for a log; opts.face is wall, floor or ceiling for a button or lever; opts.rotation is a standing sign's, 0 (its face south), 4 (west), 8 (north) or 12 (east): the only four a turtle gives; opts.hanging is a lantern's: true hangs it under the block above (placed from below, or sideways with nothing under the cell to stand on), false stands it on the block below; opts.axis is a chain's too. opts.toward = { x, y, z }, the cell a reader stands in, turns a sign to them: a wall sign when the map shows a sturdy block behind the cell (on the far side from the reader), else a standing sign at the nearest of the four rotations (how.toward says which, and how many degrees off the reader's way it is). Other opts: move (passed to T.moveTo; default { path = true, scan = false }), inside (a protected area the job may dig and walk in), tries (approaches to try, default 6), text (a sign's: wrapped to 4 lines of 15 characters, a newline starting a line; more is refused), temp (a block to put above the target for a moment, below), digBelow (below), exit ({ x, y, z }: below). A cell that already holds the item as wanted comes back as it is; one holding anything else is not touched. A placement that closes the turtle in (no way, through what the map shows empty or unknown, out of where it stands: a dozen blocks, or to opts.exit) is made with how.warning saying so; with opts.exit it's refused. When the plain ways have run out, a top half (a slab, stair or trapdoor) is placed from below with support: with nothing above it to place against, a temporary block goes there first (a cobblestone, dirt, planks or bricks on board, or opts.temp) and is taken away again; with a floor under it, only when opts.digBelow = true, the floor is dug to stand in and put back after with the same block (carry one, unless the floor comes back as itself when dug, as soul soil, planks or bricks do, and a slot is free for it); on solid ground, with no free cell beside the floor, a floor cell beside it with air above (not protected, no liquid beside it) is dug and stood in too, the floor dug from there, and both put back as they were (its block needed too). Without digBelow the floor is never dug, and the failure says the option is there, with whatever else digging it would need. Returns the block's name, its state, and { approach, from, heading, tries, lines, support } (approach is front, down or up; from the cell the turtle stood in; lines a sign's text; support { temp, floor, exit }: the names of the block put above and the floor dug, and the neighbour dug too ({ x, y, z, name }); toward, with opts.toward: { form = "wall", facing, behind } or { form = "standing", rotation, wanted, off, note }). A failure's why names the approaches tried and what each got, and what the others lack ("from below from 0,0,3: needs a block above the target, and the map has minecraft:air at 0,2,3"; "...: the map has minecraft:stone there": the stand is taken). An option it doesn't take is refused, named.

== A sign in front of a reader ==

T.signFor(reader, said, opts)
    Put a sign in front of a reader standing at reader = { x, y, z }, its face toward them, with text on it: the sign's name, its state and how ({ at, look, toward, ... } as T.placeAt's); nil and why if it can't.

    The way the reader looks is opts.look (a compass way), else toward the nearest wall the map shows at their eye level, 2 or 3 cells away. The sign goes, the first the map allows: at eye level (the reader's y + 1) on a wall 1 or 2 cells in front, standing on the floor 1 or 2 cells in front, at eye level standing on a block in front; T.placeAt with opts.toward = reader places it (a wall sign facing them, or a standing one turned the nearest a turtle can). The sign is opts.item, else the first on board. Needs the world origin. Other opts go to T.placeAt (move, inside, tries). A refusal names each cell and why it wouldn't do.

== Lighting a fire ==

T.ignite(x, y, z, opts)
    Light a fire in the cell x, y, z with flint and steel, from above: the fire's name, or nil and why.

    The turtle goes to the cell over it and uses the flint and steel downward on the block under it, which puts the fire in the cell between (so there must be a solid block under the cell, and the cell empty). Inside an obsidian frame that lights a nether portal, and what it finds is nether_portal. opts.move and opts.inside are as for T.placeAt. Returns the name of what burns there (minecraft:fire, soul_fire or nether_portal), and true if it was already burning.

tl.store: chests at home: where they are, what is in them, fetching from them and putting away

Loaded by turtlelib the first time one of its functions is used (T.addChest, T.forgetChest, T.chests, T.catalogue, T.where, T.fetch, T.stow, T.sortChests, T.recount, T.inventoryReport, T.prepare, T.autoDump), or when T.cfg.autoDump is set.

A chest is known by where the turtle stands to reach it, as the junk chest is (T.setJunkChest): the cell x, y, z in the turtle's frame, and the side the chest is on ("up", "down", or a heading 0 to 3).  T.addChest tells the turtle about one, T.catalogue goes round them and writes down what each holds, T.where says which have an item, T.fetch goes and takes some, T.stow puts what the turtle carries away (into a chest for that item, else one that already holds it, else into the bulk chest) and T.autoDump is that done for you when the inventory nearly fills: T.cfg.autoDump = true (or a number of free slots) and every dig is followed, when the room has run out, by a trip to the chests and back.  With no chests known it takes the junk chest's trip instead (T.dumpJunk).  T.inventoryReport adds up what the chests and the turtle hold, and T.prepare readies the turtle for a job in one trip: what isn't needed put away, what is fetched, the room checked.

A chest may be for some things: T.addChest's holds, globs of the items it is for ("*_log", "cobblestone").  T.stow puts those there first, and T.sortChests moves what is in the wrong chest to where it belongs.

A chest is one record however it is reached: a second stand for the same chest (the cell the stand and side point at) is the same chest, and so are the two halves of a double chest (each half is a peripheral listing the whole of it), which T.catalogue finds out from the halves' block states (by their facing when the world origin is known, else by two halves side by side holding the same).

The chests and what they held when last looked at are in the data file .chests, so every program on the turtle shares them and a restart keeps them.  A line "chest x y z side bulk|plain seen" starts a chest ("seen" the time it was read, in seconds), "other x y z" after it is the other half's cell for a double chest, "holds glob ..." what the chest is for (none: anything), and the lines "item count name" are what it held.  Fetching and stowing read the chest again as they go, and so does crafting at a known chest (T.recount: the chest beside the turtle read again), so the list stays right; a chest someone else emptied is found out the next time it is visited.

== The list of chests, in a data file ==

T.addChest(x, y, z, side, bulk, opts)
    Tell the turtle of a chest: it stands at x, y, z (the turtle's frame), the chest on `side` ("up", "down" or a heading 0 to 3); opts.holds: globs of what it is for. True (and a note if known or changed), or nil and why.

    The heading is T.dir's; "top" and "bottom" are up and down. Nothing is visited: T.catalogue reads what is in it. With `bulk` true it becomes the bulk chest, where T.stow puts what no chest holds already (there is one bulk chest; the earlier one is a plain chest again). Adding a chest again, from this stand or another, or the other half of a known double chest, keeps the one record and what was written down of it, and the note says which it is ("already known: the other half of the double chest at 3,0,1, reached from 3,0,0 side 0"). Kept in the data file .chests.

    opts.holds says what the chest is for: a glob of item names, or a list or set of them (T.addChest(3, 0, 0, 0, { holds = { "*_log", "*_planks" } })); T.stow puts those there before anywhere else and T.sortChests moves them there. Given again for a known chest it changes them, and the note says so; false makes it a chest for anything again; left out, they stay as they were. Holds that overlap another chest's are warned of in the note, chest by chest: the item names both take, from what the chests hold and the turtle carries (three, and how many more), and which glob wins, the more specific. opts may come in bulk's place, with opts.bulk.

T.forgetChest(x, y, z, side)
    Forget the chest at this place (as T.addChest was given it, or another stand for the same chest). True, or false and why.

T.chests()
    The chests the turtle knows, as a list of { x, y, z, side, bulk, seen, other, holds, items = { name = count } }.

    seen is when the chest was last read (seconds, the clock T.catalogue uses), 0 if never; other is the other half's cell of a double chest; holds the globs of what it is for (T.addChest), nil for anything.

== Going to a chest ==

T.recount(side)
    Read the known chest on `side` of the turtle ("front", "top"/"up", "bottom"/"down") again, into the list of chests. The chest as T.chests gives it, or nil and why.

    T.fetch and T.stow do this as they go, and T.craft and T.craftBatch at a chest the list knows; call it after your own drops into a known chest or pulls from it, so T.where, T.inventoryReport and T.craftPlan count what is there now. Nothing moves.

== Cataloguing ==

T.catalogue(spots, opts)
    Go round the chests and note what each holds: only the spots given ({ x, y, z, side }: the turtle's stand, the chest's side), else every chest known. True, info; false, why, info if some couldn't be read; nil, why.

    `spots` is a list of chests as { x, y, z, side } (and bulk = true for the bulk chest, holds as T.addChest takes), which are remembered (T.addChest) and read, and only they; nil goes round every chest already known. The two halves of a double chest become one chest as they are read (see the top of this module). opts.find, a box in the map (six numbers, as T.map.find takes), adds the chests and barrels the map shows in it, each from a free cell beside it, and reads those (with the spots, if any given) and no others. opts.move is T.moveTo's (default { path = true, scan = false }). The nearest comes next and the turtle ends where it began, facing as before. Info is { chests, kinds, items, failed = { { x, y, z, side, why } } }.

== Where an item is, and fetching it ==

T.where(name)
    Which chests hold the item `name` (or a glob of item names; the namespace may be left out), as written down: a list of { x, y, z, side, count, bulk, seen, age }, the nearest to the turtle first, and the total. Moves nothing.

    It is the list T.catalogue made, kept right by T.fetch and T.stow as they go; seen is when the chest was read (seconds) and age how long ago that was, so an old count can be read again first. Nil and why when no chest is known.

T.fetch(name, n, opts)
    Go to the chests that hold `name` (or a glob) and take n of it (default 1), then come back facing as before (opts.stay: stay at the last chest). Returns how many came aboard, and why if that is short of n.

    `name` is an item's name (minecraft: assumed), or a glob of them as T.where takes ("*_sword"): at each chest the items that match are taken, by name. The chests come nearest first, each read again as it is visited (so a chest that no longer has it is put right in the list and the next is tried); it stops when it has n or the turtle has no room. opts.move is T.moveTo's; opts.stay saves the walk back when another chest is next.

== What there is, everywhere ==

T.inventoryReport(opts)
    Every item across the chests (as last read) and the turtle, with totals, sorted by name: a list of { name, total, turtle, chests, places, age }, and info { kinds, items, chests, oldest, text }. Moves nothing.

    turtle is what is aboard, chests what the chests held when T.catalogue (or a fetch or stow since) last read them, places how many chests hold some, and age the seconds since the oldest of those counts was read (nil: aboard only). info.text is the report as lines ("cobblestone 164: turtle 20, 2 chests, read 5m ago"). opts.match (a name, a glob, a list or set of them) reports only those; opts.sort = "count" puts the most first.

== Putting away ==

T.stow(opts)
    Put what the turtle carries away, each item into the nearest chest that will have it, within 48 blocks (as near: one for it, then one holding it, then the bulk chest). True, info; false, why, info if some stayed aboard; nil, why.

    By default it puts away what is junk (T.isJunk: not kept by T.keep, not crafted this job, not a tool, fuel, a bucket or a peripheral); opts.all puts away what the job keeps as well (the end of a job), still never a tool, fuel or a peripheral. With T.cfg.tools set, the tools it doesn't name (but not one equipped) are put away too. It goes to the nearest chest that wants something, drops what that chest should have, reads it again for the list and goes on, then comes back facing as before. The chests that will have an item are a chest for it (its holds; the most specific holds win, T.addChest), one that holds some already and isn't for other things, and the bulk chest: of those, the nearest, and of those as near (8 blocks more at most), the first of that order. Chests over opts.maxDistance (48) from where it began (or opts.near, { x, y, z }) aren't gone to unless opts.far: an item with only those stays aboard, the why saying where the one it would go to is (the nearest chest for it, else holding it, else the bulk chest) and how far (two bases: the other one's chests aren't a trip for a few items); opts.box ({ x1, y1, z1, x2, y2, z2 }) takes only the chests in it. A chest for other things never takes an item, and a full chest for it sends it on to the next place. What no chest is for or holds, with no bulk chest, or what does not fit, stays aboard. Info is { stowed, chests, left = { name = count }, reasons = { name = why } }: each item left aboard with why, every chest it was tried at ("chest at 3,0,1 full, bulk chest at 0,0,-3 full", "no chest holds it and no bulk chest"), and the why returned says them all. opts: move (T.moveTo's), keep (names, a list or set, globs too, that stay aboard whatever), stay (stay at the last chest), maxDistance, far, near, box.

== Sorting the chests ==

T.sortChests(opts)
    Move what is in the wrong chest to the chest it belongs in (T.addChest's holds), at most opts.limit stacks (32). Returns true, info; false, why, info when some couldn't move; nil, why.

    In the wrong chest is an item in a chest for other things, or one in a chest for anything (or the bulk chest) that a chest is for. It goes to each chest with something in the wrong place (as last read: T.catalogue first after changes by hand), nearest first, reads it again, takes those stacks out while the turtle has room (two slots free), and takes each load where it belongs as T.stow would (a chest for it, else one holding it, else the bulk chest; never back into a chest for other things). What has no room there goes back to the chest it came from, and what has nowhere to go at all is not taken out. The turtle comes back facing as before (opts.stay: stays at the last chest).

    It sorts one site: the chests no more than 48 blocks apart from the one nearest the turtle (or opts.near, { x, y, z }), never moving an item from one site to another (two bases each keep their own); opts.box ({ x1, y1, z1, x2, y2, z2 }) sorts the chests in it instead, each site among them within itself. It is bounded: opts.limit stacks at most (32 by default), and info.more says there is more to do. It walks: the fuel is about the round of the chests with something misplaced and of the chests it goes to, once for every load (up to the turtle's free slots less one), and each stack takes a pull and a drop (a few ticks). Info is { moved = { name = count }, stacks, chests, more, left = { { name, count, from, why } } }: left is what couldn't move, each with the chest it is in and why; the why returned says them all. opts: limit, move (T.moveTo's), stay, near, box.

== Getting ready for a job ==

T.prepare(spec)
    Get ready for a job in one trip, T.prepare{ need = { [name] = n }, freeSlots = k }: stow what isn't needed, fetch what is, come back, check the room. True, info; false, why, info (what is short, too few slots free); nil, why.

    spec.need is { [name] = n }: what the turtle should carry (names, minecraft: assumed), spec.freeSlots how many slots must be empty after (default 0). The chests' list (as last read) is checked first: if they and the turtle together hold too little of something it refuses before moving, naming what is short, unless spec.partial. Then it stows everything that isn't needed (but never a tool T.isEssential keeps, fuel or a peripheral; what is needed stays aboard whole), fetches what is missing, nearest chest first, and comes back facing as before (spec.stay: stays at the last chest). Then it counts again: anything still short, or fewer free slots than asked, is a failure that says what. spec.move is T.moveTo's. Info is { fetched = { name = n }, stowed, short = { { item, need, have } }, free }.

T.autoDump()
    Make room: stow what is not kept (T.stow), or dump the junk (T.dumpJunk) if there are no chests; T.cfg.autoDump = true runs it when the inventory is nearly full. The results are those of the one it ran; nil and why if neither is set up.

    T.cfg.autoDump is true or a number of free slots (2 for true): after a dig that leaves that few (part stacks merged first), the turtle makes this trip and comes back where it was, facing as before. A trip that fails, or leaves no more room than that, is printed and noted in the job (T.job.note) and not tried again until there is less room; two in a row turn T.cfg.autoDump off.

tl.world: the map and the frames: what the turtle has seen, dug and placed, and where that is in the world

Loaded by turtlelib the first time one of these is used (T.scan, T.map, T.setOrigin, ...), and from the start on a turtle that already has a map on disk, so that digs and moves made by any program keep it right.  Coordinates in the calls are the turtle's own (the frame it counts in: (0,0,0) where its job started, facing +z, +x to its right).

Frames.  The turtle's frame isn't fixed: `--here`, T.setHomeHere, T.clearPos and a run with no saved position make wherever it stands (0,0,0) again.  So the map keeps a frame of its own, the one it was started in, and the transform (a shift and quarter turns) from the turtle's current frame to it.  Whenever turtlelib re-zeroes it tells this module where that spot was, and the transform is updated, so what the map holds stays where it is.  If the frame was lost without that (the saved position was deleted) the map is kept but marked unaligned: it answers nothing and takes nothing new until T.alignMap says how the frames sit, or T.map.clear starts a new map.  The world is one more transform: T.setOrigin gives the turtle's place in the world and the way it faces (from GPS and a scan if it isn't told), and T.toWorld and T.toLocal convert.  They are kept in the data folder (.map/frame).  With GPS (ADR-0018), T.checkedPos checks the saved position against a fix when a job starts: the first fix sets the origin (or anchors a player's to GPS), later ones correct the count within T.GPS_REACH blocks, and a lost position is found again, so the map stays aligned.

The map.  One file per 16 by 16 by 16 cube of space in the data folder's .map: a text header (when it was seen, the names of the blocks the cube holds, and the block states that were inspected) and then one byte a cell (4096 of them, written in binary mode): 0 for a cell never seen, 1 for air, 2 and up for a name of the palette.  A cube is loaded when it's used and written when it changed, in batches (not for every cell).  The map is capped at the smaller of 512 KB (the setting map.maxBytes) and a quarter of the disk, and the cubes unseen longest are dropped first, except those the cap keeps: the cubes a protected area or a pinned box (T.map.pin, kept in .map/pins in the map's frame) overlaps, and those holding home or the map's own origin; when only those are left the map says it is over its cap (T.map.stats().over, printed once) rather than growing without a word.  What the turtle dug, placed and moved through (T.onChange) goes in as it happens; a scan fills in the cells it covered, air where it lists no block.

A cell's "when" is the time its cube was last seen, in seconds (os.epoch "utc").

== Frames and the world ==

T.frameChanged(old, new)
    Tell the map the turtle's frame changed: the spot that was `old` ({x, y, z, dir}) is now `new` (default 0,0,0 facing 0). turtlelib calls it; returns true, or false and why.

    turtlelib calls it when a program re-zeroes (T.setHomeHere, --here, T.clearPos then a start) or corrects the heading (T.setDir), so what the map holds stays where it is. With old nil, nobody knows where the spot was: a map holding cubes is marked unaligned. False and why if the map is unaligned now or was already.

T.alignMap(dx, dy, dz, turns)
    Say how the turtle's frame sits in the map's, and mark the map aligned. Returns true, or nil and why.

    A point (x, y, z) of the turtle's frame is the map's after turning `turns` quarter turns to the right (about the vertical axis, from (0,0,0)) and then adding (dx, dy, dz). Use it after a lost position, when you know where the turtle is relative to something in the map.

T.origin()
    The turtle's frame in the world: { x, y, z, facing, aligned }, the world cell of its (0,0,0) and the compass way its +z points. Nil and why if T.setOrigin hasn't been told.

    facing is "north", "east", "south" or "west".

T.setOrigin(x, y, z, facing)
    Say where the turtle stands in the world: world cell (x, y, z), facing "north", "east", "south" or "west". Returns true and T.origin()'s table, or nil and why.

    Also n/e/s/w, or -z/+x/+z/-x. Called with no arguments it asks GPS for the cell and works out the facing from a geo scan; with x, y, z only, it finds the facing from a scan. A third result is a note when jobs saved in the turtle's frame are on disk (mine.job, an unfinished T.build's .build): they are in the frame as it was when they were made, so if that has moved since (a re-zero, --here) their cells are wrong.

T.toWorld(a, b, c)
    Convert a point of the turtle's frame (a table with x, y, z, or three numbers) to the world's: a table { x, y, z }; nil and why if there's no origin or the map is unaligned.

T.toLocal(a, b, c)
    Convert a world point (a table with x, y, z, or three numbers) to the turtle's frame: a table { x, y, z }; nil and why if there's no origin or the map is unaligned.

== The position from GPS (ADR-0018) ==

T.gpsCheck(saved)
    Check a saved position (T.loadPos's, or nil) against a GPS fix: T.checkedPos's work (ADR-0018).

    Returns the position to use (saved, corrected and saved again, or found when it was lost), a line saying what happened (nil when nothing did), true third when GPS puts the turtle beyond T.GPS_REACH (nothing corrected: the caller stops), and true fourth when there's no origin and no saved position to set one from.

T.gpsHere()
    Where the turtle stands in its frame by GPS, and the way it faces: { x, y, z, dir }, or nil and why.

    For a start with --here when GPS puts the turtle far from where it was saved (T.startAtHome): the spot becomes home, and the map and the world origin follow, so later checks agree. The facing comes from a scan, else a step.

== The map ==

T.map.get(x, y, z)
    What the map holds at x, y, z (turtle frame): the block's name, its state table if inspected, and when it was last seen (seconds); nil and why if never seen.

    Air is "minecraft:air". An unaligned map gives nil and why too.

T.map.set(x, y, z, name, state)
    Note a cell in the map by hand: the block `name` (nil: forget it) at x, y, z of the turtle's frame, with its state table if it's known. True, or nil and why. (Digs, placements, moves and scans note themselves.)

T.map.top(x, z, lo, hi)
    The y of the highest solid cell known in the column x, z (not air, water, lava or fire), and its name; nil and why if the map knows none. lo and hi (optional) keep to the cells from y lo up to y hi.

T.map.find(pattern, box, limit)
    The cells in the box (whole map if none) whose block name matches the glob, nearest first: a list of {x, y, z, name}, and true if cut to `limit` (default 500).

    The glob may leave out the namespace ("*_stairs", "stone"). Nil and why if the map is unaligned.

T.map.count(pattern, box)
    How many cells inside the box (the whole map if none) hold a block whose name matches the glob (as in T.map.find). Nil and why if the map is unaligned.

T.map.heights(box)
    A height map of the box (17 by 17 about the turtle if none) as text: each column's highest solid y, "." where none is known.

    Rows run from the box's high z down to its low z, columns from low x to high. Nil and why if the map is unaligned.

T.map.slice(y, box)
    The layer at height y in the box (17 by 17 about the turtle if none) as text, a character a cell, with a legend of the symbols.

    "." is air, "?" never seen, "~" water, "^" lava, any other symbol a block listed after. Rows run from the box's high z down to its low z, columns from low x to high. Nil and why if the map is unaligned.

T.map.flush()
    Write what has changed to disk now (it is written in batches as it goes). True, or false and why.

    When the map is over its cap with only the cubes it keeps left (see T.map.pin), it is true and that, said.

T.map.stats()
    What the map takes: { cubes, bytes, cap, unsaved, aligned, kept, pins, over }: how many cubes, how many bytes they take on disk, the most it may take, how many cubes have changes not written, and whether it is aligned.

    kept is how many cubes the cap never drops (protected areas, pinned boxes, home), pins how many boxes are pinned, and over, when the map is over its cap with only kept cubes left to drop, says so (nil otherwise).

T.map.pin(box)
    Keep the cubes of a box (six numbers in the turtle's frame, or x1 to z2 fields) when the map is over its cap. True, or nil and why.

    The cap drops the cubes unseen longest; it never drops a pinned box's, a protected area's or home's. Pins are kept beside the map (.map/pins) in its own frame, so a re-zero doesn't move them; T.map.unpin lets one go.

T.map.unpin(box)
    Let a pinned box go (the same six numbers T.map.pin was given), or every pin with no box. True, or false and why.

T.map.clear()
    Throw the map away: every cube (and every pin) is deleted. An unaligned map becomes aligned again, with the turtle's frame as its own (and the world origin is forgotten, as it was set against the old frame).

T.map.frame()
    The frame the map is in relation to the turtle's: { turns, dx, dy, dz, aligned } (see T.alignMap).

T.map.toMap(x, y, z)
    A point of the turtle's frame in the map's: mx, my, mz (T.map.frame says how they relate).

T.map.fromMap(mx, my, mz)
    A point of the map's frame in the turtle's: x, y, z.

T.map.cube(cx, cy, cz)
    The cube at cx, cy, cz (map frame) as its 4096 bytes and its palette, for code that reads many cells at once; nil if there is none.

    A cell's cube is its map coordinate divided by 16, rounded down. string.byte(bytes, (ly * 16 + lz) * 16 + lx + 1) is the cell at lx, ly, lz in the cube: 0 never seen, 1 air, 2 and up palette[code - 1].

== Scans ==

T.scan(r, opts)
    Geo-scan around the turtle (radius r, default 8; over 8 needs opts.force) into the map: { ["x,y,z"] = name } in the turtle's frame, and an info table.

    opts: force; map = false (leave the map alone); air = false (don't note the cells the scan lists no block for as air). The info table is { radius, blocks, fuel (paid), merged, why (if not merged) }; nil and why if it can't scan. The scanner is put on for the scan (T.withPeripheral: the chunk controller stays on) and asked again while it cools down. The cells come from each entry's r, u and f (right, up and forward of the turtle) and the turtle's heading. A radius over 8 costs a lot of fuel (16 once cost about 5300; 8 or less is cheap), so it's refused unless forced.

T.mergeScan(entries, r, opts)
    Put a scan somebody else took, here, in the map: true and the number of blocks in it, or nil and why.

    entries is the list a geo scanner gives (each with name, r, u and f: right, up and forward of the turtle), radius r (default 8) the scan's, and it was taken where the turtle stands and faces now. The cells it lists no block for are noted as air unless opts.air is false. For a program that does its own scanning (mine) and wants the map to know what it saw; T.scan does the whole job when the entries don't matter. An unaligned map takes nothing.

T.scanBox(box, opts)
    Scan a whole box ({x1, y1, z1, x2, y2, z2}, turtle frame) with radius-8 scans side by side, nearest next, going to each with opts.move ({ path = true, dig = true } digs): { tiles, scanned, failed, partial }.

    It goes to each scan's centre first (T.moveTo with opts.move, default { path = true, scan = false }: round what's in the way; { path = true, dig = true } digs); a centre it can't get to (solid, or no way there) is scanned from where it got to when the centre is within the scan from there, and listed in partial as { x, y, z, from, why }. opts.radius for less (over 8 is refused, as T.scan says why, unless opts.force: 8 or less is cheap). Refuses a box that takes over 27 scans unless opts.force. failed lists { x, y, z, why } for the scans not made; nil and why if the box is no good.

== Inspecting ==

T.inspectAt(x, y, z, opts)
    Go next to the cell x, y, z, inspect it and note its block and state in the map: name, state table (nil if none), or nil and why.

    The state (a stair's facing, a slab's half) is what a scan can't give. opts.move is passed to T.moveTo (dig and so on); without it the turtle goes round what is in the way with the path finder ({ path = true, scan = false }).

T.inspectAll(list, opts)
    T.inspectAt for each cell of a list ({x, y, z} tables or "x,y,z" keys), nearest next: { ["x,y,z"] = {name, state} } and a list of {x, y, z, why} that failed: the way to get block states over an area (T.scan gives names only).

    Each time it goes next to the nearest one (greedy, not the shortest tour), and looks at any other cell beside it from there.
