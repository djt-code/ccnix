turtlelib: shared helpers for the turtle programs

Usage in a program (same directory):
    local T = require("turtlelib")

Provides:
  * dead-reckoned position/heading (T.pos, T.dir, T.face), kept right by the turtle API itself: loading this wraps the moves and turns (forward, back, up, down, turnLeft, turnRight) and the digs and places, once however many programs load it, so a move made straight through turtle.* is counted too; T.raw holds the originals
  * protected areas (T.protect, T.unprotect, T.protected, T.inside) that no dig through the turtle API goes into, and a refusal to dig chests, barrels, shulker boxes, spawners and ComputerCraft blocks (T.cfg.digContainers lifts it)
  * change hooks: T.onChange(fn) hears every successful dig, placement and move
  * T.moveTo: a move to a cell in three dimensions that says why it stopped (blocked, protected, lava), T.withPeripheral and T.equipPeripheral: use an item as a peripheral without taking off a chunk controller, T.pull: a count of one item out of a chest, and a junk chest (T.setJunkChest, T.isJunk, T.dumpJunk) that nothing is ever dropped on the ground for
  * the map and the frames (tl.world, loaded when first used): T.scan, the geo scanner's blocks in the turtle's own frame, kept in a map on disk (T.map.get/find/heights/slice, ...) that digs, placements and moves update, T.setOrigin/T.toWorld/T.toLocal for world coordinates, and T.inspectAt for block states; a re-zeroed frame (--here) keeps the map right
  * routes (tl.path, loaded when first used): T.path, A* over the map round protected areas, lava, fire and doors, and T.travel, which walks one along a clear layer (or the search), planning again at a block it did not expect; T.moveTo's opts.path asks for it
  * placing (tl.place, loaded when first used): T.placeAt puts a stair, slab, log, torch, door or the like down with the state wanted (facing, half, axis), choosing how to place it from a table of what each approach gives, checking and trying another way if the game differed, and remembering what it learnt; T.ignite lights a fire from above
  * building (tl.blueprint, loaded when first used): a plan is layers of text with a legend (T.blueprint.parse/fill/box/walls/fromMap); T.build puts one up layer by layer, materials checked first, progress kept so a stop or reboot carries on; T.verify says which cells differ, states included; T.replace swaps the blocks matching a glob in a box
  * crafting (tl.craft, loaded when first used): T.craft makes stairs, slabs, walls, doors, chests and the rest of vanilla's building basics from a chest, through the crafting table equipped as a peripheral (a chunk controller stays on); recipes are data (T.addRecipe adds more), T.canCraft says what is short; T.smelt runs a furnace; T.fuelTicks and T.smeltsTo are what burns and what smelts
  * modules loaded when first used: a function T lacks that is in T.registry is looked up there, its module (turtle/tl/<name>.lua, required as "tl.<name>") fills T in, and the call goes on
  * fuel management that refuels from inventory mid-task (T.ensureFuel)
  * low-level moves that only dig blocks listed in T.diggable
  * six directions (0..3 and "up"/"down"): look, dig, place or move in one, the fewest-turns ordering, 3D positions and keys
  * a learned 2D obstacle map with BFS routing (T.goTo)
  * two column-stepping strategies: flat (fixed height) and terrain (climb steps, follow the ground, refuse crevasses)
  * inventory helpers (items by name or by a test), tool hot-swapping, serpentine plan generation
  * chest-below helpers: dump with a keep policy, count, restock, merge part stacks
  * reading item names and saved files with lib/scan and lib/text, not Lua patterns; the files with lib/fileio
  * the programs' options (T.options, on lib/getopt) and mine's job file (T.loadMineJob, T.saveMineJob: mine and autostart read it)

Programs configure it by setting fields on T.cfg and T.diggable before moving.  Everything is relative to where the turtle starts: (0,0,0) facing +z, with +x to its right.

== Position persistence ==

T.dataPath(name)
    The path of a data file kept next to the running program (/ccnix/turtle for one in the ROM), moving an old copy down the first time it's asked for.

    The programs moved from the repo's top folder into turtle/ on 2026-10-28; a file left up there (a job half done) is moved down the first time it's asked for, so `--resume` and `reset` still find it. A program in ccnix's ROM (/rom/ccnix/turtle) keeps its files in /ccnix/turtle, where its updates go too (the ROM is read-only); one from an install before ccnix (/cc-turtles/turtle) is moved there the same way.

T.savePos()
    Write T.pos, T.dir and T.mode to the position file, so a stop or a reboot can still find the way home. Raises "Terminated" if a Ctrl+T was held back (see T.run).

T.run(fn, ...)
    Run fn(...) so that Ctrl+T can't leave the saved position wrong: one that comes during a turtle command is held back until the move or turn is saved.

    Plain Ctrl+T stops a program wherever it's waiting, in the middle of a turtle command too: the turtle still moves or turns, but the program never records it, so its saved position or heading is off by one and going home from there goes astray. Under T.run a Ctrl+T that comes during a command (or a peripheral call) is held back until it's done: the program stops at the next saved move or turn (T.savePos), or the next ordinary wait (sleep, a key), whichever comes first.

T.loadPos()
    The saved position as { x, y, z, dir, mode }, or nil if there is none.

T.clearPos()
    Delete the saved position file: the next job starts from home as (0,0,0).

T.startAtHome(force)
    Call at the start of a job: the turtle is at home, facing forward. If a saved position says otherwise, returns it instead of resetting so the program can warn the user.

    Where it does reset, the spot the turtle stands on becomes (0,0,0) in a new frame; the map (T.map, if one is kept) is told where that spot was in the old one, so it stays right. With no saved position (the file was deleted) and no T.clearPos before it, nobody knows where that was, and the map is marked unaligned (T.alignMap).

== The turtle API, wrapped once ==

T.claim()
    Make this module the one the wrapped turtle functions keep up to date. Loading turtlelib does it already; call it when another program's module may have loaded since (claude, after run_program).

T.onChange(fn)
    Call fn(event) for every successful dig, placement and move from now on, by any program on this turtle; event.kind is "dig", "place" or "move", with x, y, z. Returns a function that removes the listener.

    For "dig", x, y, z is the cell, was the block's name and state the block's state table, as the inspect before it gave them; for "place", x, y, z is the cell and item the name of what was placed, if the slot's details have it; for "move", x, y, z is the cell it arrived at and from = { x, y, z }.

    A listener's error is dropped (except Ctrl+T), so one can't stop the turtle. Listeners last until the computer restarts: remove yours when the program ends.

T.protect(name, x1, y1, z1, x2, y2, z2)
    Protect the box between two corners (x, y, z in the turtle's frame, either order) under `name`: a dig into it returns false, "protected: <name>". Replaces a box of the same name. Returns true, or nil and why.

T.unprotect(name)
    Remove the area called `name`. True, or false and why (none by that name).

T.protected(x, y, z, skip)
    The name of the first protected area that holds the cell, or nil. `skip`, a name, leaves that area out (see T.guarded).

T.protections()
    The protected areas, as a list of { name, x1, y1, z1, x2, y2, z2 } (copies: changing one changes nothing).

T.guarded(x, y, z)
    The name of the protected area that stops the current job from digging the cell: T.protected, but not counting the area the job is working inside (T.cfg.inside, set by T.inside). nil if none.

T.inside(name, fn, ...)
    Run fn(...) as a job that owns the protected area `name`: digging in it is allowed meanwhile (other areas still hold). Puts back what was set before, even if fn errors (the error is re-thrown); returns what fn returned.

T.neverDig(name)
    Is this block one the dig functions refuse (a container, spawner or ComputerCraft block)? mine's own list of blocks never to dig.

T.turnRight()
    Turn a quarter turn to the right, keeping T.dir and the saved position right.

T.turnLeft()
    Turn a quarter turn to the left, keeping T.dir and the saved position right.

T.face(d)
    Turn to face heading d (0 to 3, as T.dir) by the shorter way.

T.faceToward(x, z)
    Face toward an adjacent column.

T.posString()
    The position as "(x,y,z)".

T.setDir(d)
    The heading is really d (a program worked it out from what's round the turtle: the saved one can be off after a stop between a turn and its save, or a turtle put back by hand).

    That turns the frame the turtle counts in about where it stands, so the map (T.map, if one is kept) is told.

T.lookAround()
    What's beside the turtle, by quarter turns to the right of the way it faces: seen[a] is the inspect data at a turns, or false for air.

    For checking the heading, so it turns with the raw turtle calls (which leave it facing as it was) and T.dir isn't touched.

== Fuel ==

T.hasFuel(n)
    Is there fuel for n moves? (Always, with fuel turned off.)

T.refuelTo(target)
    Burn fuel from the inventory until the tank holds `target`. Only what T.fuel lists is burnt: logs, planks, sticks, chests and crafting tables burn too, but they're what chests and torches are made from.

T.homeCost()
    Fuel to get home from here: straight-line moves by default. Programs that travel at a set height or dig down to a chest override it.

T.ensureFuel()
    Called before every move: when the tank is short of the trip home plus T.cfg.fuelMargin, tops it up from the inventory; if that isn't enough, runs T.fuelTrip, else waits for the user once truly out.

    On the trip itself, or with no T.fuelTrip set, it waits for the user once truly out, rather than starting another trip.

T.totalFuelAvailable()
    Fuel in tank plus the fuel value of the T.fuel items in the inventory. Burns nothing.

T.requireFuel(needed)
    Block until at least `needed` fuel is available (tank + inventory), filling the tank up to `needed` from inventory first.

== Tool upgrades ==

T.isTool(name)
    Is the item `name` a tool (a pickaxe, hoe, shovel, axe or sword)?

T.emptySlot()
    The first empty slot, or nil if there is none.

T.findSlot(what)
    The first slot holding `what` (an item name, or a function(name, item) that picks one); nil if none.

T.equipped(side)
    Name of the item equipped on `side`, or nil. Uses getEquippedLeft/Right (CC:Tweaked 1.110+); older versions are probed by swapping through an empty slot, which needs one free slot.

T.findTool(suffix)
    A tool whose name ends with `suffix` ("_pickaxe"): the one equipped, else the first in the inventory; nil if there's none.

T.usePrimaryTool(name)
    Equip `name` from the inventory if it isn't already, unequip any OTHER tool into the inventory, and return a function that restores the original arrangement. Errors if the tool is nowhere on the turtle.

T.withTool(name, fn)
    Run fn with `name` as the only equipped tool, restoring the original tools afterwards even if fn errors (the error is re-thrown).

T.equipTool(name, side)
    Back-compat: equip `name` onto `side` from the inventory, if present.

== Peripheral upgrades ==

T.equipPeripheral(name)
    Equip the item `name` on the side that holds no chunk controller (or kept side), and wait for it to show up. Returns the peripheral and a function that puts back what was there, or nil and why.

    It prefers an empty side, then one with a tool, then another upgrade. Call the returned function when done (calling it again does nothing). The reasons for nil: not on board, a tool rather than a peripheral, both sides kept, no free slot for what comes off, or it never showed up.

T.withPeripheral(name, fn)
    Run fn(peripheral) with the item `name` equipped as a peripheral, and put back what was on that side afterwards. Returns true and what fn returned, or nil and why it couldn't equip (see T.equipPeripheral).

    The side is put back even if fn errors (the error is re-thrown).

== Low-level moves ==

T.up()
    Move up one block, digging what T.diggable lists and attacking what's in the way (fuel first). True, or false if anything else is in the way or T.cfg.maxHeight is reached.

T.down()
    Move down one block, digging what T.diggable lists and attacking what's in the way (fuel first). True, or false if anything else is in the way or T.cfg.maxDrop is reached.

T.forward()
    Move forward one block, digging what T.diggable lists and attacking what's in the way (fuel first). True, or false if anything else is in the way.

T.back()
    Back up a block without turning (saves turning round to go back the way it came). It can't see or dig behind it: false if anything is there.

T.settle()
    Sink until resting on something solid.

T.toY(y)
    Climb or sink to height y in the current column.

T.toStartHeight()
    Return to y = 0.

T.below()
    What is directly below: a block name (or "air"), plus inspect details.

== Six directions ==

T.sideDir(side)
    The direction a side (CC's "front", "top", "bottom", as for chests) is in from the turtle as it faces now.

T.here()
    A copy of T.pos: { x, y, z }.

T.at(p)
    Is the turtle at p ({ x, y, z })?

T.posKey(p)
    The key "x,y,z" for a position p.

T.keyPos(k)
    Inverse of posKey: the x, y, z of "x,y,z" (whole numbers, as posKey writes them); nil if k isn't one.

T.dist(a, b)
    The taxicab distance between two positions.

T.neighbour(d)
    The block next to the turtle in direction d.

T.dirTo(p)
    The direction from the turtle to the block next to it at p.

T.look(d)
    Face direction d (0 to 3, "up" or "down") and inspect there: returns turtle.inspect's ok, data.

T.digDir(d)
    Face direction d (0 to 3, "up" or "down") and dig there, through the wrapped dig, so a protected area holds. Returns turtle.dig's results (false and why if it can't).

T.placeDir(d)
    Face direction d (0 to 3, "up" or "down") and place the selected item there. Returns turtle.place's results.

T.attackDir(d)
    Face direction d (0 to 3, "up" or "down") and attack there. Returns turtle.attack's results.

T.suckDir(d)
    Face direction d (0 to 3, "up" or "down") and pick up items there. Returns turtle.suck's results.

T.moveDir(d)
    Move one block in direction d (T.up/T.down/T.forward: digging what T.diggable allows, attacking what's in the way).

== Moving to a cell in three dimensions, and saying why it stopped ==

T.moveTo(x, y, z, opts)
    Move to the cell x, y, z (the turtle's frame), digging only what opts.dig allows. Returns true, or false, why, the block's name and cell where one stopped it. opts: order, dig, avoid, inside, path.

    It goes along the axes in the order opts.order names (default "yxz": up or down first, then x, then z). opts (all optional):
      dig     false (default), true, a glob or a list of globs: the blocks it
              may dig on the way (a protected area, a chest or a computer is
              never dug)
      avoid   a glob or a list: blocks it stops at rather than enter
              (default: lava, fire and doors); {} avoids nothing
      inside  the name of a protected area the move may dig in (see T.inside)
      path    true, or a function(x, y, z, opts): when a straight run is
              blocked, ask a route finder (T.travel, from the path module, if
              there is one; or this function) to take it the rest of the way
    The why is a sentence: "blocked by minecraft:obsidian at 3,12,-4", "protected: castle (...)", "avoiding minecraft:lava at ..."; the cell is { x, y, z }. The turtle stays wherever it got to. (T.cfg.maxHeight and maxDrop, a program's grid, don't apply.)

T.turnsTo(d)
    Turns it takes to face direction d (none for up or down).

T.eachAround(skip, fn)
    Call fn(d) with each direction but `skip`, the fewest turns away first (so up and down, and the way it faces, come before any turn).

T.stepToward(p)
    A step toward p (nearer by taxicab distance), the one needing the fewest turns; nil when there.

== Obstacle map (2D, by column) and BFS routing ==

T.ckey(x, z)
    The key "x,z" for a column.

T.keyXZ(k)
    Inverse of ckey: the x, z a key ("x,z") was made from; nils if k isn't one.

T.markBlocked(x, z)
    Mark column x, z as blocked, for T.bfs and T.goTo.

T.clearBlocked()
    Forget every column marked blocked.

T.inBounds(x, z)
    Is column x, z inside the routing area (T.cfg.width and length, plus T.cfg.margin)?

T.bfs(tx, tz)
    Shortest column path from the current position to (tx,tz), or nil.

== Column-stepping strategies ==

T.stepFlat()
    Flat: stay at the current height.

T.stepTerrain()
    Terrain: climb up to maxClimb to get in, then sink onto the ground. A drop deeper than maxClimb is a crevasse: back out and mark it.

T.goTo(tx, tz)
    Navigate to column (tx,tz) with BFS + re-planning.

T.coverColumn(x, z)
    Stretch the routing area (cfg.width/length) so it takes in column (x,z) too: a turtle stopped outside it, on a farm bigger than the defaults or one lying left of or behind home, would otherwise have no route at all.

T.goHome(opts)
    Return to the start from wherever the saved position says we are (used by the `reset` subcommands and home.lua). Returns true if home.

    In flat mode the trip is made at height opts.travelY (default 0, the start height), e.g. above tall crops. The routing area is cfg.width/length, stretched to take in the turtle's position. opts.check, if given, runs once at travel height before setting off (it may correct T.dir); false from it stops the trip.

T.setHomeHere()
    `reset --here`: the turtle was put back by hand, so accept where it is (facing forward) as home without moving.

T.requireHome(force, prog)
    Start a job: startAtHome, but when the saved position says the turtle is elsewhere, print the standard warning (naming the program's reset command) and return false so the program can stop.

T.setting(name, default, description)
    A setting from CC's settings (`sysctl mine.width=5` at the prompt), defined here so `sysctl -d` describes it with its description; its default where there is no settings API.

T.saveSettings(values)
    Keep values given on the command line ({ [name] = value }) as the settings, so the next run without them (or the autostart) uses them.

T.options(args, long)
    Parse a program's command-line `args` with lib/getopt, options and operands in any order. Returns the options table and the operands, or nil and why.

    `long` lists the long options: name = true for a flag, "=" for one with a value. A dash word that isn't one of them stays an operand.

T.loadMineJob()
    The job: { width, height, length (nil: no end), spacing, homes, state }, or nil if there's none or it isn't one.

T.saveMineJob(job)
    Save a job as loadMineJob reads it back.

T.hasMineJob()
    Whether a mine.job file is there at all (a job that can't be read still counts: mine was given one).

== Plans ==

T.serpentine(width, length)
    Serpentine over the grid: columns along x, rows alternating in z. Tiles are counted OUT from the start: x = 1..w, z = 1..l (signed), so the start tile (0,0) is never part of the plan.

T.lightLattice(radius, width, length)
    Positions for light sources so that every tile of the grid is within taxicab distance `radius` of one. Returns a set keyed by T.ckey and an ordered list.

    It uses the diamond lattice generated by (r, r+1) and (r+1, -r), which tiles the plane with L1 balls exactly, and clamps lattice points that fall outside the grid onto its edge (which can only shorten their distance to tiles inside).

    Computed on a 0-based grid, then shifted to the 1-based, signed grid the plan uses; the start tile (0,0) is outside it and never gets a torch.

== Inventory ==

T.selectItem(what)
    Select the first slot holding `what` (a name, or a function(name, item)); false if there's none.

T.countItem(what)
    How many of `what` the turtle carries.

T.tidyInventory()
    Merge part stacks of the same item, move part stacks into the empty slots ahead of them and select slot 1, so what's picked up next joins its stack. Returns how many slots it freed.

    Picked-up items go into the first slot, counting on from the selected one, that is empty or holds the same item (CC:Tweaked's InventoryUtil), so an empty slot ahead of a part stack starts a second stack of it. A move takes as long as a step (a failed one hardly any); with nothing to do it only reads the slots.

T.inventoryFull()
    Is every slot taken?

T.freeSlots()
    How many slots are empty.

T.isContainer(name)
    Is the block name a chest or a barrel?

T.containerBelow()
    Is there a chest or barrel below the turtle? (T.containerOn("bottom"))

T.wouldDump(keepCount)
    Would dumpDown(keepCount) get rid of anything?

T.dumpDown(keepCount)
    Drop inventory into the container below. Returns false if there is no container below; otherwise true and how many items didn't fit (the container is full).

T.dumpDownWait(keepCount, interval)
    dumpDown, but while the container is full, stop and wait for room, checking every `interval` seconds. Returns false if there is no container below.

T.inventoryLine(label)
    Print one line listing what the turtle is carrying.

T.ensureRoom(need, keepCount, goDump, warning)
    Make sure at least `need` slots are free before working a tile whose drops must not spill, calling goDump() (the trip to the chest) if short. Returns true, or false once still short (printing `warning` once).

    It only calls goDump when dumping with keepCount would free something, and stops making trips that free nothing (no chest) until slots open up again.

== Containers ==

T.dropSide(side, n)
    Drop up to n items from the selected slot into whatever is on `side` ("front", "top" or "bottom"): turtle.drop's results.

T.suckSide(side, n)
    Pick up up to n items from `side` ("front", "top" or "bottom") into the selected slot.

T.inspectSide(side)
    turtle.inspect on `side` ("front", "top" or "bottom"): ok, data.

T.containerOn(side)
    Is there a chest or barrel on `side`?

T.containerCounts(side)
    How many of each item the container on `side` holds ({ name = count }), or nil if it can't be read.

T.countContainer(side, name)
    How many `name` the container on `side` holds, or nil if it can't be read.

T.compactContainer(side)
    Tidy the container on `side`: merge part stacks so everything sits in as few slots as it can, then sort it.

    Hoppers and the turtle's own partial takes leave small stacks scattered about; it fills the earliest part stack from the latest, then sorts (sortContainer). Uses the container's pushItems.

T.restockFrom(side, name, target, opts)
    Pull `name` out of the container on `side` until the turtle holds `target` of it (opts: label for messages, quiet, room: free slots to leave, default 1).

    Sucking from a side always takes from the container's first occupied slot regardless of what it is, so with a readable container the wanted stack is moved to the front first (frontStack) and exactly what's needed is taken. Otherwise anything else that comes out is set aside and dropped back once we're done (fuel is kept).

T.takeInto(side, name, n, slot)
    Take `name` from the container on `side` into the turtle's slot `slot` (empty, or holding some of it already) until that slot holds n (at most a stack). Needs a readable container. Returns how many the slot holds.

T.pull(side, name, n)
    Take n (default 1) of the item `name` out of the container on `side` ("front", "top" or "bottom") into whatever slots will have it. Returns how many it got and, when short of n, why.

    A part stack of it is topped up first, else an empty slot is used. Sucking from a side takes the container's first stack whatever it is, so each time the wanted stack is moved to the front first (as T.takeInto does), and as many stacks are taken as it needs. Needs a container it can read (a chest or a barrel). When short of n, why is: no container, none left in it, or no room in the turtle.

== Junk ==

T.setJunkChest(x, y, z, side)
    Remember the junk chest: it stands on `side` of the cell x, y, z (the turtle's frame): "up" or "top", "down" or "bottom", or a heading 0 to 3. True, or nil and why.

    The heading is T.dir's: 0 is +z, 1 is +x. Kept in a data file, so every program on the turtle uses the same one.

T.junkChest()
    Where the junk chest is, as { x, y, z, side } (side a heading 0 to 3, "up" or "down"), or nil if none is set.

T.markCrafted(name)
    The craft module calls this for each item it makes, so it is never junk for the rest of the job (until the computer restarts, or T.clearCrafted()).

T.clearCrafted()
    Forget what T.markCrafted named: the end of a job.

T.isJunk(name)
    Is the item `name` junk? False for what's in T.keep, tools, fuel, buckets, a crafting table, peripherals and what was crafted this job.

T.dumpJunk()
    Go to the junk chest, put every junk stack in it and come back facing as before; nothing is dropped unless a chest is there. Returns true, items dropped, items left; or false and why.

    It looks at the chest first, and what doesn't fit stays aboard. With no junk on board it goes nowhere. The reasons for false: no junk chest set, no way there, no chest there.

T.refuelFrom(side, target)
    Burn fuel from the container on `side` until the tank holds `target`, fuel on board first; empty buckets go back in. True if the target was reached.

    It takes one item of a kind to learn what it's worth, then only as many as are needed (capped at the tank's limit).

== Modules loaded when first used ==

T.need(name)
    The function T.<name>: as it is, or from the module the registry names, loading that first. Returns it, or nil and why (not a function of T, or its module wouldn't load or lacks it).

tl.blueprint: plans of what to build: the format, building it, checking it, and swapping blocks in a place

Loaded by turtlelib the first time T.blueprint, T.build, T.verify or T.replace is used.  Cells are the turtle's own (the frame it counts in).

A plan is layers of text with a legend, bottom layer first.  As a file it reads:

  name: tower
  anchor: 10 64 -3
  B = minecraft:stone_bricks
  s = minecraft:stone_brick_stairs[facing=north,half=bottom]
  layer 1:
  BBBB
  B..B
  layer 2:
  ssss

Each character is a cell: "." is air, a space is "leave alone" (not built, not checked), anything else is looked up in the legend.  The text is a map seen from above with +z at the top, as T.map.slice shows one: the first line of a layer is the highest z, a column goes toward +x, the next layer is one up.  The anchor is the turtle-frame cell of the first character of the first line of the first layer.  A state is in brackets after the name, key=value separated by commas; a name without a namespace is minecraft:'s.  The same plan as a Lua table: { name, anchor = {x, y, z}, legend = { B = "minecraft:stone_bricks", s = "...[facing=north]" }, layers = { "BBBB\nB..B", { "ssss" } } } (a layer is a string of lines or a list of lines).  The helpers fill, box, walls and fromMap make one from code; put changes a cell.

T.build puts a plan up.  It checks the materials first (what is short, and what could be crafted if the craft module is there), then goes layer by layer from the bottom, standing over each cell and placing down; in a layer the plain blocks come first, then stairs and slabs, then what hangs on others (torches, ladders, buttons, trapdoors, gates), then doors, so a thing goes in after its support.  A stair, slab, log, torch or door goes through T.placeAt for the state it names.  The plan is kept as text in the data file .build, and how far the build has got (the number of the last cell tried and the cells that failed, with why) in .build.progress, so a stop, a crash or a reboot carries on where it was with a plain T.build().  A build never digs a block out of a cell it fills (T.replace swaps blocks).  A finished build can protect itself (opts.protect).

T.verify walks the plan and says which cells differ, states included: a cell with a state to match, or that the map has never seen, is looked at with T.inspectAll; the rest is read from the map.  T.replace swaps every block matching a glob in a box for another, each from its nearest free side; one with no free side is reported, never dug to.

    The blocks are as the map has them, with their states if they were inspected, air as ".", cells the map has never seen left alone.

T.blueprint.new(source)

== Building ==

T.build(plan, opts)
    Build a plan: its cells placed in the order the overview gives, with the materials checked first and the progress kept. Returns true, info; false, why, info when it stopped or cells failed; nil, why when it couldn't begin.

    `plan` is a plan (table or text); nil carries on the build saved in the data file after a stop, a crash or a reboot. The same plan again carries on too; a different plan while one is unfinished is refused unless opts.restart. It first counts what the cells still to do need against what is on board, and refuses if anything is short (the reply's third value lists { item, need, have, short }, and what T.canCraft says if there is such a function) unless opts.partial; cells with no item left fail one by one. A cell that fails is noted and the build goes on; the failed ones are tried again at the end of a later run (opts.retry = false leaves them). Nothing is dug out of a cell it fills: a block in the way is a failure. A cell the map already shows holding the block (with its state) is taken as done without a look, so a plan built over itself, or carried on after a crash, goes quickly; opts.look goes and looks at every cell instead. opts: at ({ x, y, z }: build with the plan's anchor here), look, move (for T.moveTo; default { path = true, scan = false }), inside (a protected area the job owns), limit (the most cells to try in this run), restart, partial, retry, protect ("keep", true or an area name: protect the finished build under the plan's name, or that name; only when no cell failed). Info is { name, done, total, failed = list of { n, x, y, z, item, why }, placed (cells put in this run), there (cells found already in place), finished, resumed, protected, short }.

== Checking ==

T.verify(plan, opts)
    Check a plan against the world: the cells that differ, as a list of { x, y, z, want, wantState, found, foundState, why, unverified }, and { checked, inspected, differing, unverified }; nil and why if it can't start.

    `plan` is a plan; nil checks the saved build. Every cell the plan does not leave alone is compared: the block's name, and each key of the state the plan names. A cell with a state to match, or that the map has never seen, is looked at with T.inspectAll (opts.inspect = "all" looks at every cell); the rest is read from the map, which the build keeps right. A cell that could not be looked at is listed too, with unverified = true. An empty list means the build is as planned. opts: at ({ x, y, z }), scan (true: scan the box with T.scanBox first), inspect, move (for the walking), inside.

== Swapping blocks ==

T.replace(box, pattern, item, opts)
    Swap every block in a box whose name matches a glob for another block: how many, and what could not be. Returns true, info; false, why, info when some were trapped or failed; nil, why when it couldn't begin.

    The box is six numbers in a table, or { x1 =, ... }; the glob matches block names (the namespace may be left out); `item` is the block to put in, with a state in brackets if it has one. The cells are those the map holds (opts.scan scans the box first, which the map needs to know it). Each is taken from the nearest free side the map shows, nearest next: the turtle looks at the block (one that has changed since is left), digs it and places the new one. A block with no free side (every neighbour solid in the map) is listed in `trapped` and never dug to. It refuses if there is less of `item` on board than cells to swap, unless opts.partial. Info is { replaced, same, trapped, failed, gone, more }, trapped and failed being lists of { x, y, z, name, why }. opts: scan, limit (cells at most, default 1000), move (for T.moveTo), inside (a protected area the job owns, to swap blocks in it), partial.

tl.craft: crafting and smelting: recipes as data, T.craft, T.canCraft, T.smelt, and what burns and smelts

Loaded by turtlelib the first time one of its functions is used (T.craft, T.canCraft, T.recipe, T.addRecipe, T.smelt, T.fuelTicks, T.smeltsTo).

Recipes are written as the game's data packs write them: up to three rows of letters (a dot is an empty cell), what each letter stands for (a name, a list of names or a glob like "*_planks", minecraft: assumed), what comes out and how many.  A family is one entry: "minecraft:{}_stairs" over a list of blocks makes every one's stairs, the {} being the block's name without its ending (oak_planks gives oak, stone_bricks gives stone_brick); a map entry gives the block each result is made from (chiseled forms from their slabs).  T.addRecipe adds more, for modded items.  The table is T.RECIPES (it exists once this module has loaded), the newest first.

A turtle crafts through the crafting table as a peripheral, and only when every slot outside the grid is empty.  So T.craft works from a chest: it checks the chest has room for the whole inventory, puts the crafting table on (through T.withPeripheral: a chunk controller stays on), stashes everything in the chest, the pickaxe too, pulls each round's ingredients into the grid's slots (1-3, 5-7 and 9-11), crafts, stashes again, and at the end puts the inventory back and the product with it.  What it made is never junk (T.markCrafted).  T.canCraft says what is short, from the inventory and the chest.  A craft does the recipe asked for; an ingredient that is itself crafted (planks from logs, sticks from planks) is made first with its own T.craft.

T.smelt runs a furnace: a furnace takes fuel through its sides, the item through its top, and gives the result through its underside only.  It sets the furnace up in front of the turtle, one block up, so the cell under it is free to stand in, drops the fuel from beside, the item from above, sucks the results from below as they cook (ten seconds an item), and takes the furnace back.  What burns and how long (T.fuelTicks; the nether's woods do not) and what smelts into what (T.smeltsTo) are tables: T.FURNACE_FUEL and T.SMELTS.

== Reading and adding recipes, and asking what is short ==

T.addRecipe(spec)
    Add a recipe (modded items, say): out (the item made), count, shape, key, mixed, and for a family of, from or map. True, or nil and why not.

    spec = { out = "mod:widget", count = 2, shape = { "AA", "B." }, key = { A = "minecraft:iron_ingot", B = "*_planks" } }. A letter in the shape is a name, a list of names or a glob (a name with no namespace is minecraft:'s); a dot is an empty cell; mixed = true lets one letter stand for different items (any planks). A family has out with {} in it and of = "X" for the letter that is the block, with from = a list of blocks, or map = { result = block }. The newest recipe is tried first. Kept in memory only: put the calls in /claude/helpers.lua to have them each session.

T.recipe(name)
    The first recipe that makes an item: { out, count, shape, key, mixed } or nil and why.

    shape is the rows of letters, key what each letter is (a name, a glob, a list of names; for a family the block this item is made from), mixed whether one letter may be several items. There may be more than one recipe for it; this is the first (the newest added, else the built-in).

T.canCraft(name, n, opts)
    Can the item be crafted: true, or false, why and the short list. Counts the inventory and the chest.

    name is the item, n how many to have (default 1; whole crafts, so more may come out). The chest is the container opts.chest names (front, top or bottom) or the first there is; nothing moves. Returns true and { crafts, makes }; or false, a sentence ("short of oak_planks: need 6, have 4") and the list of { item, need, have, short }. It does the one recipe asked for: an ingredient that is itself crafted, planks from logs, counts as short.

== Crafting from a chest ==

T.craft(name, n, opts)
    Craft n of an item from a chest (stash the inventory, fill the grid, craft, put it all back): true and how many, or false/nil and why.

    It works from a chest: the container in front, above or below, or opts.chest (a side, or { x, y, z, side } to walk to), else the junk chest. The chest needs room for the whole inventory; that is checked first, and so are the ingredients (inventory plus chest) and a crafting table (on board, equipped or in the chest). Then the table goes on (a chunk controller stays on), everything is stashed in the chest, the grid is filled from it and crafted, round after round, and the inventory comes back with the product. n is rounded up to whole crafts. opts: chest, partial (craft what the ingredients allow), move (for T.moveTo).

    Returns true, made; or false, why, made (it made some, or could not carry them); or nil, why (nothing was touched): no recipe, short of an ingredient (the third value is the list from T.canCraft), no chest, no room in the chest, no crafting table. What it made is marked as crafted, so T.isJunk never says it is junk.

== Fuel and smelting ==

T.fuelTicks(name)
    How many ticks a furnace burns the item for (20 a second; it smelts an item in 200), or nil if it is not a fuel.

    Coal and charcoal 1600, a block of coal 16000, a lava bucket 20000, planks, logs and wooden things 300 or less. The nether's woods (crimson and warped stems, planks and the rest) do not burn. The table is T.FURNACE_FUEL.

T.smeltsTo(name)
    What the item smelts into in a furnace, or nil if it does not smelt.

    Ores and raw metals to ingots, cobblestone to stone, sand to glass, clay to bricks, logs to charcoal (not the nether's stems), raw food to cooked. The table is T.SMELTS.

T.smelt(item, n, fuel, opts)
    Smelt n of an item in a furnace the turtle carries, set up in front of it: true and how many came out, or false/nil and why.

    The furnace goes up in front of the turtle, one block above it, so the cell under it is free to stand in. Five cells must be free: the two over the turtle, the one in front of it, and the two over that (where the furnace stands and above it); opts.move = { dig = true } lets it dig them (opts.move is for T.moveTo). Fuel goes in from beside, the item from above, and the results are sucked from below as they cook (ten seconds an item, at most 64 at a time); then the furnace is taken back and the turtle comes home, facing as before. fuel is an item name (default: charcoal, coal, then planks or logs, whichever there is enough of). What it makes is marked as crafted.

    Returns true, got; false, why, got (it did not all come out in time); or nil, why (nothing started): not smeltable, short of the item or the fuel, not a fuel, no furnace on board.

tl.path: routes: a search over the map for a way to a cell, and walking it

Loaded by turtlelib the first time T.path or T.travel is used (T.moveTo asks for T.travel when a straight run is blocked and opts.path is set).  Cells are the turtle's own (the frame it counts in).

T.path finds a route: A* in three dimensions over the map (tl.world), with a binary heap.  What a step into a cell costs depends on what the map holds there:
  known air or water
      one move
  a block it may dig
      a move and a dig (opts.dig says what may be dug, as for T.moveTo)
  a cell never seen
      a move and a dig when digging everything is allowed; otherwise a move and a penalty, so a route through the unseen is possible but the known is preferred (it is checked as it is walked)
  a wall
      never: a protected area (except the one opts.inside names, and except the empty cells of an area the route starts or ends in), what opts.avoid lists (lava, fire and doors unless it says otherwise), a block it may not dig (a chest, bedrock, anything opts.dig leaves out), and any cell in opts.avoidCells
The search reads the map's cubes as strings (string.byte), not as tables of cells, so a big search stays cheap in memory; it gives the rest of the computer a turn about every half second (CC stops code that goes seven seconds without yielding), and gives up past a limit of cells searched, saying so.

T.travel goes there.  From the map it looks for a clear layer, a height at which the whole way is known to be empty, between the highest floor and the lowest ceiling on the way (the Nether has a roof: a fixed height hits bastion ceilings): up, across, down.  If the map doesn't know enough it scans the route's box first; if there is no layer it uses the search.  Then it walks the route.  A block it didn't expect stops a step: it notes the block in the map and plans again from where it is, a few times.

== The search ==

T.path(x, y, z, opts)
    A route to the cell x, y, z through the map: a list of cells to step into, one after another, the last being the goal (empty when already there); nil and why if there is none.

    It starts from where the turtle is (opts.from = { x, y, z } to plan from elsewhere). The costs and the walls are in the overview of this module. A second result gives { nodes, cost, digs, unknown }: how many cells the search looked at, the route's cost, and how many of its cells need a dig or were never seen. Nothing moves. opts (all optional):
      dig        false (default), true, a glob or a list of globs: what a route may dig (as for T.moveTo)
      avoid      a glob or a list: blocks a route stays out of (default: lava, fire and doors; {} avoids nothing)
      inside     the name of a protected area the route may dig in (default T.cfg.inside, see T.inside)
      avoidCells a list of { x, y, z } cells a route may not use
      limit      cells to search before giving up (default 20000)
      margin     how far outside the box of the two cells it may look (default 24)

== Walking a route ==

T.travel(x, y, z, opts)
    Go to the cell x, y, z by the map: along a clear layer if there is one, else by a search; true, or false and why.

    Up, across and down at a height where the map shows the whole way empty (the lowest climb first); if the map doesn't know enough to find one it scans the route's box first (T.scanBox, once; opts.scan = false skips that); with no layer, T.path's search. Each stretch is walked with T.moveTo. A block it did not expect stops a step: the block is noted in the map, the cell is kept out of the next plan, and it plans again from where it is, up to opts.replans times (default 6). opts are T.path's (dig, avoid, inside, avoidCells, limit, margin), plus span (how far above the higher end a layer may be, default 8), scan, replans, and scanning's opts.move. On failure the turtle stays where it got to.

tl.place: placing blocks the right way round: stairs, slabs, logs, torches, doors and the rest, and lighting a fire

Loaded by turtlelib the first time T.placeAt or T.ignite is used.  Cells are the turtle's own (the frame it counts in).

A turtle does not choose how a block lands.  What it gets depends on how the turtle places it, because the game has the turtle's fake player click a block, and the block's state comes from the click (CC:Tweaked's TurtlePlaceCommand, and Minecraft's rules for each block).  The game tries, in order: a block already in the target cell, the block BEYOND the target (clicked on the face toward the turtle), for a sideways place the block under the target (clicked on its top), and last the turtle's own block.  A sideways click lands just below the middle of a face, so what that gives is, in short:
  sideways
      stairs and slabs bottom half, the stair facing the turtle's heading; a log lying along the heading with a block beyond (standing with only a floor); a torch, ladder, button or lever hung on the block beyond; a door, gate or chest facing as the turtle does
  placeDown
      stairs and slabs bottom half if there is a block under the target, else top half
  placeUp
      stairs and slabs top half if there is a block over the target, else bottom half
(With nothing to click but the turtle's own block, a sideways stair faces back at the turtle.) The table of what each approach yields is data (T.PLACE_TABLE): per family of block, per approach (front, down, up), rows that say "if there is a block beyond (or a floor under the target), these state values".  A row's value is a plain word (half=bottom) or relative to the turtle's heading: facing=heading, back, right or left, and axis=along (the heading's) or across.  The rest of this comment is how it is used.

T.placeAt(x, y, z, item, { facing, half, axis }) works out which approaches the table says give that state and the map (tl.world) says are possible, goes to the nearest, places, inspects, and if the state came out wrong digs the block and tries the next.  Facing is a compass name, so it needs the world origin (T.setOrigin: the compass way the turtle's frame points); half and axis do not.  Where the map does not know what is beside the target the approaches are only guesses and go last.  What actually came out is remembered per family, in the data file .placements, but only when the map knew every fact the row depended on: a table row that was wrong is corrected once, for every later placement.  A door goes in after the walls round it, and needs a solid block under it and the cell above free; T.ignite lights a fire from above with flint and steel.

== Placing a block with the state wanted ==

T.placeInfo(item)
    What placeAt can place this item by: { family, keys, hang, door }, or nil if the item is not a block it knows.

    family is stairs, slab, log, torch, ladder, button, door, trapdoor, fence_gate, chest, fence, pane, wall or block; keys is the set of state names placeAt can be asked for with it (facing, half, type, axis, face: a slab takes half and type, which are the same); hang is true for a family that hangs or stands on a solid block; door is true for a family of two blocks. Used by tl.blueprint to order the work and to ask for only the states that can be asked for.

T.placeAt(x, y, z, item, opts)
    Place item at the cell x, y, z with the state wanted (opts.facing, opts.half, opts.axis): the block, its state and how; nil and why if it can't.

    It works out from the table which approaches (placing sideways, from above or from below, from each side) give the state wanted and the map says are possible, goes to the nearest with T.moveTo, places, inspects, and if the state is wrong digs the block and tries the next approach, learning what the game actually gave (see the overview). opts.facing is a compass name (north, east, south, west) and needs the world origin; opts.half is bottom or top for a stair, slab or trapdoor; opts.axis is x, y or z for a log; opts.face is wall, floor or ceiling for a button or lever. Other opts: move (passed to T.moveTo; default { path = true, scan = false }), inside (a protected area the job may dig and walk in), tries (approaches to try, default 6). A cell that already holds the item as wanted comes back as it is; one holding anything else is not touched. Returns the block's name, its state, and { approach, from, heading, tries } (approach is front, down or up; from the cell the turtle stood in).

== Lighting a fire ==

T.ignite(x, y, z, opts)
    Light a fire in the cell x, y, z with flint and steel, from above: the fire's name, or nil and why.

    The turtle goes to the cell over it and uses the flint and steel downward on the block under it, which puts the fire in the cell between (so there must be a solid block under the cell, and the cell empty). Inside an obsidian frame that lights a nether portal, and what it finds is nether_portal. opts.move and opts.inside are as for T.placeAt. Returns the name of what burns there (minecraft:fire, soul_fire or nether_portal), and true if it was already burning.

tl.world: the map and the frames: what the turtle has seen, dug and placed, and where that is in the world

Loaded by turtlelib the first time one of these is used (T.scan, T.map, T.setOrigin, ...), and from the start on a turtle that already has a map on disk, so that digs and moves made by any program keep it right.  Coordinates in the calls are the turtle's own (the frame it counts in: (0,0,0) where its job started, facing +z, +x to its right).

Frames.  The turtle's frame isn't fixed: `--here`, T.setHomeHere, T.clearPos and a run with no saved position make wherever it stands (0,0,0) again.  So the map keeps a frame of its own, the one it was started in, and the transform (a shift and quarter turns) from the turtle's current frame to it.  Whenever turtlelib re-zeroes it tells this module where that spot was, and the transform is updated, so what the map holds stays where it is.  If the frame was lost without that (the saved position was deleted) the map is kept but marked unaligned: it answers nothing and takes nothing new until T.alignMap says how the frames sit, or T.map.clear starts a new map.  The world is one more transform: T.setOrigin gives the turtle's place in the world and the way it faces (from GPS and a scan if it isn't told), and T.toWorld and T.toLocal convert.  They are kept in the data folder (.map/frame).

The map.  One file per 16 by 16 by 16 cube of space in the data folder's .map: a text header (when it was seen, the names of the blocks the cube holds, and the block states that were inspected) and then one byte a cell (4096 of them, written in binary mode): 0 for a cell never seen, 1 for air, 2 and up for a name of the palette.  A cube is loaded when it's used and written when it changed, in batches (not for every cell).  The map is capped at the smaller of 512 KB (the setting map.maxBytes) and a quarter of the disk, and the cubes unseen longest are dropped first.  What the turtle dug, placed and moved through (T.onChange) goes in as it happens; a scan fills in the cells it covered, air where it lists no block.

A cell's "when" is the time its cube was last seen, in seconds (os.epoch "utc").

== Frames and the world ==

T.frameChanged(old, new)
    Tell the map the turtle's frame changed: the spot that was `old` ({x, y, z, dir}) is now `new` (default 0,0,0 facing 0). turtlelib calls it; returns true, or false and why.

    turtlelib calls it when a program re-zeroes (T.setHomeHere, --here, T.clearPos then a start) or corrects the heading (T.setDir), so what the map holds stays where it is. With old nil, nobody knows where the spot was: a map holding cubes is marked unaligned. False and why if the map is unaligned now or was already.

T.alignMap(dx, dy, dz, turns)
    Say how the turtle's frame sits in the map's, and mark the map aligned. Returns true, or nil and why.

    A point (x, y, z) of the turtle's frame is the map's after turning `turns` quarter turns to the right (about the vertical axis, from (0,0,0)) and then adding (dx, dy, dz). Use it after a lost position, when you know where the turtle is relative to something in the map.

T.origin()
    The turtle's frame in the world: { x, y, z, facing, aligned }, the world cell of its (0,0,0) and the compass way its +z points. Nil and why if T.setOrigin hasn't been told.

    facing is "north", "east", "south" or "west".

T.setOrigin(x, y, z, facing)
    Say where the turtle stands in the world: world cell (x, y, z), facing "north", "east", "south" or "west". Returns true and T.origin()'s table, or nil and why.

    Also n/e/s/w, or -z/+x/+z/-x. Called with no arguments it asks GPS for the cell and works out the facing from a geo scan; with x, y, z only, it finds the facing from a scan.

T.toWorld(a, b, c)
    Convert a point of the turtle's frame (a table with x, y, z, or three numbers) to the world's: a table { x, y, z }; nil and why if there's no origin or the map is unaligned.

T.toLocal(a, b, c)
    Convert a world point (a table with x, y, z, or three numbers) to the turtle's frame: a table { x, y, z }; nil and why if there's no origin or the map is unaligned.

T.map.get(x, y, z)

T.map.set(x, y, z, name, state)

T.map.top(x, z)

T.map.heights(box)

T.map.slice(y, box)

T.map.flush()
    Write what has changed to disk now (it is written in batches as it goes). True, or false and why.

T.map.stats()
    What the map takes: { cubes, bytes, cap, unsaved, aligned }: how many cubes, how many bytes they take on disk, the most it may take, how many cubes have changes not written, and whether it is aligned.

T.map.clear()
    Throw the map away: every cube is deleted. An unaligned map becomes aligned again, with the turtle's frame as its own (and the world origin is forgotten, as it was set against the old frame).

T.map.frame()
    The frame the map is in relation to the turtle's: { turns, dx, dy, dz, aligned } (see T.alignMap).

T.map.toMap(x, y, z)
    A point of the turtle's frame in the map's: mx, my, mz (T.map.frame says how they relate).

T.map.fromMap(mx, my, mz)
    A point of the map's frame in the turtle's: x, y, z.

T.map.cube(cx, cy, cz)
    The cube at cx, cy, cz (map frame) as its 4096 bytes and its palette, for code that reads many cells at once; nil if there is none.

    A cell's cube is its map coordinate divided by 16, rounded down. string.byte(bytes, (ly * 16 + lz) * 16 + lx + 1) is the cell at lx, ly, lz in the cube: 0 never seen, 1 air, 2 and up palette[code - 1].

== Scans ==

T.scan(r, opts)
    Geo-scan around the turtle (radius r, default 8; over 8 needs opts.force) into the map: { ["x,y,z"] = name } in the turtle's frame, and an info table.

    opts: force; map = false (leave the map alone); air = false (don't note the cells the scan lists no block for as air). The info table is { radius, blocks, fuel (paid), merged, why (if not merged) }; nil and why if it can't scan. The scanner is put on for the scan (T.withPeripheral: the chunk controller stays on) and asked again while it cools down. The cells come from each entry's r, u and f (right, up and forward of the turtle) and the turtle's heading. A radius over 8 costs a lot of fuel (16 once cost about 5300), so it's refused unless forced.

T.scanBox(box, opts)
    Scan a whole box ({x1, y1, z1, x2, y2, z2}, turtle frame) with radius-8 scans side by side, nearest next: { tiles, scanned, failed }.

    It goes to each scan's centre first (T.moveTo with opts.move, such as { dig = true }); opts.radius for less. Refuses a box that takes over 27 scans unless opts.force. failed lists { x, y, z, why } for the scans not made; nil and why if the box is no good.

== Inspecting ==

T.inspectAt(x, y, z, opts)
    Go next to the cell x, y, z, inspect it and note its block and state in the map: name, state table (nil if none), or nil and why.

    The state (a stair's facing, a slab's half) is what a scan can't give. opts.move is passed to T.moveTo (dig and so on).

T.inspectAll(list, opts)
    T.inspectAt for each cell of a list ({x, y, z} tables or "x,y,z" keys), nearest next: { ["x,y,z"] = {name, state} } and a list of {x, y, z, why} that failed.

    Each time it goes next to the nearest one (greedy, not the shortest tour), and looks at any other cell beside it from there.
