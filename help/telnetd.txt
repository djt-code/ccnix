telnetd: a telnet server: a shell, or the console, over the network

  telnetd
      serve (run it as a service: see below)

Any telnet client can connect (ours is `telnet`).  After the password, each connection gets a shell of its own, sized to the client's screen: ccsh if ccsh.login is on, else the CraftOS shell; leaving it closes the connection.  With telnetd.attach set to "console" it gets the console instead, whatever runs there (the miner's screen, the farmer's...): what's on the screen is shown, and what's typed goes to it as if typed here, but Ctrl+T doesn't (Telnet's "interrupt process", Ctrl+] then t in our client, does).  A session's shell leads a session of its own on terminal pts/n (ps shows it): what's typed goes to what's in front there, as on the console.  The screen goes as ANSI escapes with xterm's 256 colours.

Settings: telnetd.password (what to type at "Password:"); telnetd.open (true: no password at all); telnetd.attach ("console", or "" for a shell each); telnetd.port (23); telnetd.facility (local6: the system log's facility; the rules file it in /var/log/telnetd.log).  It won't start without a password unless telnetd.open is on.  The password crosses the network as typed, as with any telnet.

telnetd needs init, which runs its shells as processes, and the network (`ip up`).  To keep it running in the background:
  service add telnetd telnetd
  service enable telnetd          (at boot)
  service start telnetd
deploy/setup telnetd does all that.  Who connects, logs in or gives a wrong password is logged (`help syslog`): /var/log/telnetd.log, and `service status telnetd` shows the last of it.
