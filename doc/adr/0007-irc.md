# ADR-0007: IRC: a client, a server with services, and the game's chat

**Status:** Accepted (2026-11-09). Built in ccnix 0.35.0; simmed, not yet
tried in game (UNTESTED.md, IRC)
**Date:** 2026-11-09
**Deciders:** Dan Theisen

## Context

The user asked (2026-11-09) for "a solid irc client within minecraft",
inspired by BitchX and weechat "with irssi's plugin system", and then
"a stupid simple irc server ... learn from ngircd ... basic services
that tie into minecraft native apis", run as a ccnix service with
documentation for enabling, disabling and configuring it. They also
asked for ccnix's own readline-like library to be built as part of it.

Forces:

- **CC's screen.** 51 x 19 on a computer, 26 x 20 on a pocket, up to
  hundreds wide on monitors; 16 colours; one byte a character (Latin-1
  above 160). IRC is UTF-8 with mIRC's formatting codes.
- **The network stack** has TCP but no TLS, so real networks must take
  plain 6667.
- **One event queue.** A client must keep drawing and taking keys while
  connecting (DNS, the TCP handshake) and reading, so nothing may block.
- **The game's own APIs** reachable from CC: the world's clock
  (`os.time("ingame")`, `os.day`), a command computer's `commands`, and
  Advanced Peripherals' Chat Box, Player Detector and Environment
  Detector (the pack has AP 0.8.2a). AP renamed its peripheral types and
  changed the Chat Box's calls to an options table between 0.7 and 0.8.
- **Keep it simple** (standing preference): no security rabbit holes;
  real-protocol compatibility welcome.

## Decision

1. **A shared protocol library, lib/irc**: messages with IRCv3 tags,
   rfc1459 case folding, masks, CTCP, mIRC codes as runs, UTF-8 to and
   from Latin-1, base64 for SASL. Written with lib/scan, not patterns.
2. **The client in three layers**: lib/ircclient (state, servers,
   buffers, commands, settings, signals, scripts; no drawing),
   lib/ircui (the screen), bin/irc (the loop). Each server connection is
   a coroutine the client steps with every event, as parallel does, so
   connecting and reading wait without blocking the screen.
3. **From each inspiration:**
   - weechat: numbered buffers, the buffer list and nick list, aligned
     nicks, Alt+digit.
   - BitchX: the blue status bar, the WHOIS box, the banner, `[@nick]`
     NAMES, `/kb` and the trout.
   - irssi: signals with irssi's names (`"message public"`, `"event
     privmsg"`, `"send text"`...), `signal_stop`, `command_bind`,
     `settings_add_*`, timeouts, scripts in `~/.irc/scripts` and
     `scripts/autorun`.
   Scripts are Lua (CC has no Perl), each in its own environment, and
   everything a script registers is noted so unloading takes it away.
4. **readline grows an editor**: `readline.editor{...}` takes events one
   at a time and draws on a fixed row, with program bindings for Ctrl,
   Alt and plain keys. `read()` is rebuilt on it, so ccsh's keys are
   the same code.
5. **The server, ngIRCd-sized**: one server, no links, no flood limits.
   It speaks the commands clients use; channel modes are `o v b k l i m n s t`,
   user modes `i o`; it pings to find dead connections. lib/ircd is
   transport-free (a `send` function per client, `input` per line) so
   the sims drive it directly; bin/ircd wires it to the network the way
   httpd does (`read(0)` on `net_tcp` events) and runs under init as a
   service.
6. **Services inside the server** (lib/ircserv), as users with no
   connection: NickServ, ChanServ, MC. Passwords are kept hashed with
   salted, iterated FNV-1a: enough that they don't show, and labelled
   as not real security (anyone at the computer can read the file).
7. **The game through lib/mc**, whatever is attached, the first of
   each:
   - the clock from CC itself;
   - chat both ways with a Chat Box (a command computer's `tellraw` can
     speak but not hear);
   - players and their joins and leaves from a Player Detector (a
     command computer's `list`, polled and diffed, without one);
   - the weather from an Environment Detector.
   Both AP names and both ways of calling are tried, and the Chat Box's
   cooldown queues messages. The bridge is a channel (`#minecraft`) MC
   sits in.
   - **Tie-in:** NickServ's VERIFY whispers a code to a player in the
     game, and CONFIRM ties the nick to them (WHOIS shows it).
8. **No TLS, no DCC, no logging to files, no server linking** for now.

## Options considered

- **One program, no library split.** Simpler to start, but the server
  and client couldn't be simmed against each other in memory, and the
  200-locals limit bites a 2000-line file.
- **Lua patterns for parsing.** Shorter, but against ccnix's
  readable-parser rule.
- **Bridge players as fake IRC users** (`Steve[mc]` joining and
  parting). Truer to the game, but a burst of joins and parts and nick
  clashes. MC relaying with `<player>` is how most bridges look.
- **A mod-side peripheral** for chat and players instead of AP. More
  native, and not dependent on AP, but a mod change for something AP
  already does in the pack. It's open if AP turns out unreliable.

## Consequences

- Easier: other full-screen programs can use readline's editor; any
  program that waits on the network can use the coroutine-per-connection
  pattern; lib/mc is the game for any program, not just ircd.
- Harder: the AP calls are unverified until tried in game (both forms
  are coded for that reason).
- To revisit: TLS if the stack gets it; logging; DCC; a mod peripheral
  for the game if AP falls short.
